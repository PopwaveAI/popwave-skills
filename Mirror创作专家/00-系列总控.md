- **一次一专家**：同一时刻只有一个执行者，避免方法论混用。

## 三、通用约定

- **输入**：各专家按自身「前置输入」节要求接收（本章事件/人物/设定摘要等），素材不足时不硬写。

- **产出**：各专家直接输出最终版（正文/大纲/审查报告），不附创作说明与元评论。

- **保真**：精华节是权威内容源；专家壳只负责"什么时候调用、喂什么、拿什么、交给谁"。若壳与精华冲突，以精华为准。

- **测试**：本系列先按"专家文档"形态交付试跑，验收满意后再按需转成 popwave skill 规范（SKILL.md + skill.json + CHANGELOG）。

## 一、智能体规则管理（AgentRule）

> 取自 skill：创作工具管理 / references/agent-rules.md

用于管理当前小说的用户自定义规则。AgentRule 是**会自动注入后续聊天 prompt 的长期约束**，适合保存用户确认过的写作偏好、禁忌、章节规格、风格边界和稳定工作要求。

### 三类内容必须区分

| 内容                  | 是什么                                         | 用什么管理                                     |
| :------------------ | :------------------------------------------ | :---------------------------------------- |
| AgentRule / 用户自定义规则 | 长期约束 AI 怎么写、怎么判断（如「章节 4000-5000 字」「不写降智反派」） | `agent-rules`                             |
| AgentSkill / AI 技能  | 可按任务加载的一套流程（如「章节节奏审稿」）                      | `agent-skills`                            |
| 小说内规则 / 世界观规则       | 故事事实或设定（如「火系法术怕水」）                          | 写入世界观/角色/资料；只有用户明确要求 AI 遵守时才提炼成 AgentRule |

用户只说「新建规则」但无法判断是哪类时，先问清楚，不要直接调 Run。

### 触发条件

使用：查看/读取规则列表全文；保存偏好禁忌风格字数视角为长期规则；「以后都这样」「记住这个规则」；修改/改名/启停/删除；整理冲突。

不使用：临时写作任务且未表达长期保存；要建可调用流程（转 AgentSkill）；要保存小说资料本身。

### 工作流程要点

1. **先确认是否长期保存**：AgentRule 影响后续聊天，不存临时指令；判断不清先问。
2. **先 list 现有规则**，避免重复冲突：`Run {command:agent-rules, subcommand:list}`。
3. **判断创建/更新/合并**：同名用 update；同类不同标题先读旧的再判断；冲突让用户选；没有则 create。
4. **写好规则**：可执行、单一职责、有适用范围、不含空话（避免「写好一点」「更有爽感」）、不泄露底层错误。
5. 创建：`create {name, content}`，默认启用；可 `enabled:false` 停用创建。
6. 更新/改名/排序/启停：`update {name, content/new-name/enabled/sort-order}`。
7. 删除：只有用户明确要求才 `delete`；暂时不用优先停用。
8. 保存后回报；Run 失败直接报告，不假装已保存。

### 冲突处理格式

发现冲突按此说明，用户确认前不覆盖：

```
发现规则冲突：
旧规则：每章 2500-3000 字。
新要求：每章 4000-5000 字。
请确认后续按哪一个执行。
```

### 常见误判

- 「以后所有章节不要写降智反派」→ AgentRule。

- 「火系法术怕水」→ 通常是小说设定。

- 「以后审稿按六步检查」→ 通常是 AgentSkill。

- 「主角不能复活这条记住」→ 先写世界观；强调必须遵守再提炼 AgentRule。

## 二、智能体技能管理（AgentSkill）

> 取自 skill：创作工具管理 / references/agent-skills.md

用于把用户确认过的 AI 工作流程、写作方法、审稿规则和工具使用步骤沉淀为**应用内全局可复用**的 AgentSkill。会出现在所有小说聊天的「可用 AgentSkills」列表，可通过 AgentSkill 工具按需加载。

### 区分两类「skill」

- **AgentSkill**：约束 AI 怎么工作（如「章节扩写流程」）。用 `agent-skills` 管理。

- **小说内技能/功法/天赋/职业**：故事设定（如「火球术」）。不是 AgentSkill，禁止用 `agent-skills` 创建，写入正文/设定/角色/世界观。

### 范围

`agent-skills` 始终操作**应用内全局技能列表**，影响所有小说聊天。内置 Bundled Control Skill（如「创作向导」「创作工具管理」）不能通过该命令创建/更新/删除/安装，只能 `reference-list`/`reference-get` 只读查询附件。

### 字段

- `name`：短、可调用、全局唯一，优先中文。

- `when-to-use`：触发条件，写具体语境。

- `description`：一句话说明做什么。

- `prompt`：完整可执行指令，含步骤、边界、输出、自检；依赖小说内容时须先读取/询问，不硬编码某本书事实。

- `references`：可选 `references/**` 按需读取附件；核心规则留 prompt。

### 命令

- list → create / update（按返回 id）→ delete（仅用户明确要求）。

- Reference CRUD：`reference-list` / `reference-get` / `reference-create` / `reference-update` / `reference-move` / `reference-delete`，以全局唯一 name 定位，路径以 `references/` 开头。覆盖/移动/删除前必须 AskUser。

- 搜索安装：`search {source: official|marketplace}` → `get` → **安装前必须 AskUser 确认** → `install`。marketplace 未登录返回 login\_required 时先 `account login`。

- call\_name 冲突时用 AskUser 选「覆盖 / 新调用名 / 取消」，不自行覆盖改名。

### 质量标准

能被 when-to-use 准确触发；description 便于快速判断；prompt 隔天重载也能独立执行；不依赖本轮聊天隐含上下文；需要小说上下文时先读当前小说资料；不把小说设定当 AI 操作指令。

### 常见误判

- 「给主角设计潜行技能」→ 小说内容。

- 「审稿都查主角降智」→ 长期偏好用规则，一套流程用 AgentSkill。

- 「把刚才扩写步骤做成 skill」→ 通常是 AgentSkill。

- 「新增技能：火焰冲击」→ 小说内技能，禁止调用 agent-skills。

## 三、技能创作向导（Skill 设计）

> 取自 skill：创作工具管理 / references/skill-design.md

把模糊想法沉淀为高质量、全局可复用的 AgentSkill Bundle（Skill 元数据 + 完整 prompt + 按需读取的 references）。

### 先判定正确载体

- 小说角色功法/天赋/能力 → 故事资料。

- 只注入当前小说的长期偏好/禁忌 → AgentRule。

- 需要独立角色/委派/并行协作 → 智能体。

- 可多次按需加载的 AI 工作流程/审查方法/写作方法/工具编排 → AgentSkill。

### 设计流程

1. 先 `agent-skills list` 查重，重名则让用户选更新/合并/保留/取消。
2. 收集最小规格（每轮 AskUser 最多 2-3 问）：任务目标与成功结果；2-3 条应触发说法；1-2 条不应触发场景；必要输入/要读的资料/允许工具/产物与禁区；哪些进 Reference。
3. 输出 Bundle 蓝图：name / when\_to\_use / description / prompt / references 清单 / 验收样例（≥2 应触发、≥2 不应触发、≥1 信息不足行为）。
4. 显式确认后写入：create 一次性写完整 Bundle；改既有用 update + reference-\*。
5. 创建后验收：触发能否排除相邻任务；prompt 是否依赖本轮隐含上下文；Reference 是否确实按需读取；选一条真实任务走一遍。

> Reference 只放篇幅长、部分任务需要、可独立维护的材料；核心目标、不可违反边界、每次必做的步骤必须留 prompt。

## 四、智能体管理（Subagents）

> 取自 skill：创作工具管理 / references/subagents.md

用于管理主智能体可委派的**自定义智能体**。每个有独立名称、职责、system prompt、使用场景和启用状态。官方内置智能体不在可编辑列表，不能修改/停用/删除。

### 区分三类

- **智能体**：可承担连续性审查、节奏审稿等协作任务。用 `subagents` 管理。

- **AgentSkill**：按任务加载的流程。用 `agent-skills`。

- **小说角色/世界观人物**：写入角色或世界观，禁止创建成智能体。

### 字段

- `slug`：稳定唯一机器标识，小写英文数字下划线。

- `name`：短展示名。

- `description`：何时应委派。

- `prompt`：完整 system prompt，含职责、先读哪些上下文、步骤、边界、输出、自检。

- 可选：`mode`（chat/council，默认 chat）、`enabled`（默认 true）。

### 命令

- 先 `subagents list` 取 id，update/delete 用 id。

- create / update（只传要改字段）/ 停用启用 / 删除（固定走确认门槛：list → AskUser 明确确认 → `delete {id, confirm:true}`）。

- 不要把「清理」「不再使用」当删除确认；优先停用。

### Prompt 质量标准

明确负责什么/不负责什么；指定开始前要读的上下文；给出可执行步骤；输出含结论/依据/待核验项/可执行建议；发现冲突明确指出不平均处理；不依赖本轮隐含上下文。

## 五、工作流管理（Workflow）

> 取自 skill：创作工具管理 / references/workflows.md

管理应用内全局 Workflow：可反复运行的多步骤节点图。不是 AgentSkill，也不是小说正文里的「任务流程」。创建后出现在各小说工作流列表。

### 先读取再创建/更新

`workflows list` → 复制 id → `workflows get {id}` 读完整快照。同名/同责则更新；职责相近合并方式会改用户意图则 AskUser。

### 创建与更新

- 创建需 `name` + 完整 `graph`（start\_node\_id / nodes / edges），description 可选。

- 更新：只改名称/描述可只传改变字段；改节点图时 `graph` 是**完整替换快照**，须以 get 返回的完整 graph 为基础。

- 改单个节点用 `update-node {id, node_id, changes}`；`changes` 只传要改字段。节点类型：agent / split / loop / break / stop / humanize。

### Graph 契约

- 节点字段（\*必填）：

  - agent：id\*、type\*、name\*、prompt\*、agent\_slug、provider、model、output\_schema、sort\_order、position

  - split：id\*、type\*、name\*、prompt\*、condition\*

  - loop：id\*、type\*、name\*、prompt\*、loop\_count\*、child\_graph\*（子图只允许 agent 与 break）

  - break：id\*、type\*、name\*、prompt\*、condition\*

  - stop：id\*、type\*、name\*（只暂停等人工，不能作起始节点）

  - humanize：id\*、type\*、name\*、prompt\*、strength（very\_low/low/medium/high/very\_high）

- `output_schema` 数组：`{field, value_type(string|number|boolean), description}`；field 唯一，不能用保留名 input/last\_result。

- 变量读取：`{{outputs.<node_id>.text}}` / `{{outputs.<node_id>.json.<field>}}` / `{{outputs.<node_id>.result}}` / `{{run.input}}` / loop 内 `{{loop.iteration}}` `{{loop.count}}`。

- edge：`{id, from_node_id, to_node_id, condition(always|true|false), sort_order}`。graph 必须无环、所有节点可从 start\_node\_id 到达。

- condition：固定结构顶层 `any` 含一个或多个 `all`，组内只放 `compare`；`compare` 含 left/op/right。

### 删除

只有用户明确要求删除才执行；先 list 找 id，AskUser 确认名称与影响后 `delete {id, confirm:true}`。未确认不得传 confirm:true。
