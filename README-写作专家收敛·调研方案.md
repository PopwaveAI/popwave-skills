# 三个写作专家收敛·调研方案

> 这是一份**调研方案**，不是合并方案本身。它回答的是"如何调研、如何逐 skill 对比内容差异、用什么证据和判定框架收敛出合并方案"。
> 本方案只定方法、定流程、定产出物，不在此处执行任何合并。

---

## 1. 背景与目标

起点（`pop-qidian-*`）、番茄（`pop-fanqie-*`）、test（`test-*`）三族各自维护了一套**7~9 段的平行写作管线**。三族在结构上高度同构——几乎都有 `pipeline → 立项/原料 → world → character → plot → write → review`，下游四段（world/character/plot/write/review）更是三族齐备。这造成了两类明显代价：

- **功能碎片化**：同一职责被三套 skill 重复实现，步骤、模板、红线各写一遍，维护量 ×3，且容易漂移分叉。
- **共享资源双写**：22 份文风DNA在 `qidian-write` 与 `fanqie-write` 各落一份（44 个物理文件）；审核模板（chapter-card / state-snapshot）在 `qidian-review`、`test-review` 重复；`chapter-record.tpl` 在 `qidian-write`、`test-write` 重复。

本次调研的目标是：**用可复现的证据，逐 skill 判定"哪一段应唯一真源、哪一层应抽公共、哪个真的是差异化需要保留"**，最终产出合并方案。合并方案必须是证据驱动，而不是拍脑袋——因此先做调研。

---

## 2. 调研对象·资产地图

调研的原子单位是**一个 skill**，外加一个**跨族共享资源层**。先把边界划清楚，避免把不同尺度混在一起比。

```
                        三族平行管线（下游五段三族齐备，构成收敛主战场）

  上游(范式差异)          中游(步骤/模板差异)       下游(高收敛度)
 ┌────────────┐        ┌────────────────┐     ┌───────────────────┐
 │ pipeline   │        │ world          │     │ write (文风DNA)    │
 │ seed/adapt │   →    │ character      │  →  │ review (双文件)    │
 │ research   │        │ plot           │     └───────────────────┘
 └────────────┘        └────────────────┘
   起点/番茄/test 范式不同         三族共享一套状态快照/白描卡心智
```

**对比单元清单**（每单元出一张差异卡，详见 §3）：

| 族 | 总控 | 立项/原料 | 世界 | 角色 | 剧情 | 正文 | 审核 | 独有 |
|---|---|---|---|---|---|---|---|---|
| 起点 | pipeline | research + seed | world | character | plot | write | review | — |
| 番茄 | pipeline | seed | world | character | plot | write | review | — |
| test | pipeline | research + adapt | world | character | plot | write | review | **lite**（无对应） |

**共享资源层**（不属于单个 skill，单独一个对比单元）：

| 资源 | 所在族skill | 重复落地点 |
|---|---|---|
| 22 份文风DNA | qidian-write + fanqie-write 的 `references/文风兜底/` | 双写 44 文件 |
| 审核双文件模板 | qidian/review + test/review | chapter-card、state-snapshot |
| 章节记录模板 | qidian/write + test/write | chapter-record.tpl |
| 爬虫/清洗脚本 | fanqie/write、qidian、test 的 `scripts/` | 需逐个核实 |

> 独有项（如 `test-lite` 超轻量单文件引擎）单列，判定时走"差异化保留"而非"并入合并"。shared resource 层单独看，因为它的合并解法通常是"抽公共 + 各族引用"，与 skill 本体的解法不同。

## 3. 对比单元与统一对比维度

每个 skill 独立产出一张**差异卡（diff card）**，卡内按统一 8 维采集，三族同出名目才可比，异名异职责才不致误判。

| # | 维度 | 采集内容 | 判定用途 |
|---|---|---|---|
| 1 | 定位与触发词 | 能力声明、用户触发短语（来自可用 skill 列表 + SKILL.md 首段） | 判职责边界是否重叠 |
| 2 | 输入资产 | 消费哪些文件：立项PRD / 创意 / 设定包 / world / character / plot / 白描卡 / 状态快照 / NEXT 章节号 | 判依赖链异同 |
| 3 | 产出资产 | 落盘位置、目录约定、命名规则、引用的模板 | 判目录结构异同 |
| 4 | 工作流步骤 | SKILL.md 的 steps 数量、顺序、前置门禁 | 判流程骨架异同 |
| 5 | 范式基因 | **立项驱动 / 创意种子驱动 / 设定包改编(X)驱动** | 上游差异核心，判是否真差异 |
| 6 | 红线与门禁 | 硬约束、审核双文件、版本一致性要求 | 判红线是否漂移或冗余 |
| 7 | 共享资源引用 | 引用了哪些 references/文风DNA/templates/scripts | 判跨族复用点、双写点 |
| 8 | 强专属内容 | 本 skill 独有、跨族无对应、且有保留价值的内容 | 判唯一真源候选 |

**采集纪律**：所有内容从 `SKILL.md`、模板文件、`references/` 实际读出，不允许凭记忆或凭能力描述脑补。凡出现"两族同名不同实现 / 一名多义"的高频歧义点，单独记录进差异卡的"歧义备注"。

## 4. 调研流程（Phase 0–5）

调研自身也分层推进，先盘点、后比对、再判定、最后才起草合并方案。每 Phase 有明确出口产物，出口不过不进入下一 Phase。

### Phase 0 · 资产盘点与作用域冻结

- 冻结三族全部 skill 清单（§2 表格即为初版），把每个 skill 的 md/templates/scripts/references 文件列全。
- 产出：`00-资产盘清单.md`（每族一个子表，记录 skill 名、文件清单、版本号）。
- 出口：三族清单齐备，共享资源双写点全部定位。

### Phase 1 · 同段克隆映射

- 按 §2 的段位把三族 skill 两两对齐成"克隆组"（pipeline 组、seed/adapt 组、world 组、character 组、plot 组、write 组、review 组）。
- 每个克隆组内横向比对 §3 的 8 维。
- 命中"同名同职责"的组标 `克隆`，命中"同名不同职责/异名同职责"的组标 `歧义` 并重点标注。
- 产出：`01-克隆映射表.md`（每行一个克隆组，8 维逐格填来源）。

### Phase 2 · 逐 skill 差异卡

- 每个 skill 独立产出差异卡（§3 的 8 维 + 歧义备注）。
- 差异卡是只读分析任务，天然适配子 agent 派发（详见 §7 执行组织）。每张卡都须带"摘自 SKILL.md 的证据引用"（文件名 + 关键句），防止空回报与编造。
- 产出：`02-差异卡/` 目录，每 skill 一张，共 24+ 张。

### Phase 3 · 跨族重复/冲突检测

- 专项扫描共享资源层的重复落地点：文风DNA双写、review 双文件模板、chapter-record 模板、scripts。
- 对每处重复给出：重复了几份、内容是否已漂移、merge 成单一真源的可行性。
- 产出：`03-重复与冲突检测表.md`。

### Phase 4 · 合并判定框架落地

- 把 §5 的判定框架套到每个克隆组与每个共享资源上，逐项填"判定 + 证据 + 波及 + 风险"。
- 涉及"删除/合并"的判定，必须先过反向引用检测（grep 检查被删 skill/资源还有谁在引用），引用存在则标记"待拆引用"。
- 产出：`04-合并判定表.md`（这是合并方案的直接样板）。

### Phase 5 · 合并方案草稿

- 仅在此刻，把判定表转写成真正的合并方案：列出"抽哪些公共层、留哪个唯一真源、哪几个并行保留、删哪些冗余、怎么迁移引用、版本如何联动"。
- 合并方案是调研的**产出**，不是本方案文件的一部分（本文件到判定表为止）。
- 产出：`05-合并方案建议.md`（占位，调研完成后由执行阶段填充）。

---

## 5. 合并判定框架与门禁

对每个对比单元（skill 或共享资源），在 A / B / C 三种裁决里选一。裁决必须引差异卡与重复检测表的证据，不能空口站队。

| 裁决 | 含义 | 适用场景 | 否决条件 |
|---|---|---|---|
| **A 提炼共享层** | 抽出单一真源，各族改为引用 | 共享资源双写（文风DNA / review 双文件模板 / 状态快照心肺) | 双写已被证实内容漂移、无法对齐时降级为 C |
| **B 合并归一** | 删重复实现，各族路由到保留的一份 | 同名同职责、实现可择优 | 被删方的强专属内容会被丢弃 → 先剥离再判 |
| **C 差异化并行** | 保留，各司其职 | 范式真不同（seed vs adapt）、面向读者不同 | 判断基于"惯性复制"而非需求差异的可疑保留 |

**判定三连问**（每个 B / C 判定都要回答，答卷存进判定表）：
1. 这段职责是产品结构上的不同，还是历史路径上的复制？
2. 若合并，必然丢掉哪块内容，丢掉它意味着什么？
3. 若保留并行，是各写各的维护 ×N，还是能简化为"一组共享层 + 一个差异开关/参数"？

**门禁**：
- 任何"删除/合并"判定，必须过反向引用检测；引用未拆完不得落删除。
- 任何改动，必须同步版本三件套（`SKILL.md` / `skill.json` / `CHANGELOG.md`）。
- 共享层抽取后，必须回填各族的 `SKILL.md`（写正文仍须注入 ≥1 份文风DNA的硬约束不能因抽层而失效）。

## 6. 产出物与交付链路

调研的产出物按顺序串成一条证据链，最终喂给合并方案：

```
00-资产盘清单 → 01-克隆映射表 → 02-差异卡/（24+张）
        ↘ 03-重复与冲突检测表 → 04-合并判定表 → 05-合并方案建议
```

存放建议：`d:\popwave-skills\temp\写作专家收敛调研\`（不入 git 主干，避免与 skill 仓库混污）。

---

## 7. 执行组织与红线

**执行组织**：调研是只读分析，天然适配"子 agent 只读采集、主 agent 落盘"的模式。
- Phase 0/1 资产盘点、Phase 2 差异卡采集、Phase 3 重复检测 → 派 Explore 子 agent 并行采集，但**一次并行 ≤ 3 个**，且每份回报必须带文件证据引用。
- Phase 4 判定表、Phase 5 合并方案 → 主 agent 汇总落盘，不交子 agent 代写。

**红线**（遵循本项目既有约束）：
1. **读原点为证**：差异卡只从实际文件采集，禁止凭能力描述 / 记忆脑补。
2. **不变破下游**：凡涉删除，先做反向引用检测；下游写正文的 DNA 注入硬约束、review 的双文件沉淀，必须随抽层一并迁移而非蒸发。
3. **版本三件套同步**：任何被改/被抽层的 skill，`SKILL.md` / `skill.json` / `CHANGELOG.md` 一并更新。
4. **独有项不硬并**：`test-lite` 这类族内独有、且实现自洽的 skill，默认走 C 差异化并行，除非证据显示它已被下游吸收。
5. **决策留痕**：每个 B/C 裁决都答三连问并进判定表，合并方案引判断表为据，不做无证据合并。

**待确认项**（开工前向老板钉死，避免返工）：
- 调研范围是否覆盖 test 族全部（含 `test-lite` / `test-adapt` 与 `test-research` 的双头立项），还是只比较三者共有段位。
- 产出物存放到 `temp/` 还是单独建 `docs/` 目录。
- 本次调研是否要一次跑到底产出 `05-合并方案建议.md`，还是先走到 `04-合并判定表.md` 给老板过一眼再续。
