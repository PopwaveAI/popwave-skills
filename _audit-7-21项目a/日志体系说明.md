## 九、分析脚本清单

本目录 `scripts/` 沉淀了本次审计/追踪用到的 3 个脚本，按流水线顺序分层，前一层的输出是后一层的输入：

| 脚本 | 阶段 | 输入 | 输出 | 核心职责 |
|:--|:--|:--|:--|:--|
| `log_audit.py` | ① 深度审计 | 源项目根目录 | `log_audit_results.json` + 终端报告 | 量化存储/冗余/信息沉底/孤儿/元数据缺失 |
| `meta_extractor.py` | ② 元数据解耦 | 源项目根 + 输出目录 | `_logmeta/{runId}.json` + `index.json` | 每个 run 抽取结构化 meta，关联会话、推断成败 |
| `session_analyze.py` | ③ 会话链条分析 | `_logmeta/index.json` + 源项目 | `session_analysis.json` + 终端概览 | 按会话分组统计开销/成功率/耗时，盘点子 agent |

**运行方式**（均为标准库，无第三方依赖，需 Python 3.8+）：


## 十、分析 SOP（可复现流程）

对任意 paopao 项目做「日志审计 + 会话追踪」的完整流程，按以下顺序执行：

1. **摸清全貌** → 跑 `log_audit.py`，先量化存储分层、事件结构、冗余度、信息沉底点位，建立问题地图。
2. **解耦元数据** → 跑 `meta_extractor.py`，把 run 的成败/耗时/token/会话归属抽成 `_logmeta/index.json`，之后定位问题只读索引，不再翻原始 events.jsonl。
3. **会话链条追踪** → 跑 `session_analyze.py`，以会话为链条分组统计：开销涨幅（input 首→末/累计）、任务成功率（success/fail/partial）、子 agent 表现（status/摘要与详情长度）。
4. **可视化呈现** → 用 `session_analysis.json` 的数据做可视化（趋势折线 + 成功率构成 + 子 agent 表），形成对老板的可读结论。
5. **结论与信号** → 输出三块指标：开销涨幅拐点、成功率与失败根因、子 agent 产出是否达标（如摘要过短即预警）。

**关键解读规则**：
- 开销看「单次 input token 随会话推进的涨幅」而非累计值，累计仅看总盘子。
- 成功率失败 run 要区分**真实逻辑失败**与**良性噪声**（如登录失效 401 属环境问题，重试即成功）。
- 子 agent 看 `summaryLen`/`detailsLen` 是否与职责匹配：research 类详情应厚重，implementation-check 类过短即产出可能不达标。
