# 规划模式

大改动之前先把现状摸清，写一份施工方案，等用户确认，再按方案动手。

## 什么时候用

三条中碰任一条就走本流程：

- 改动会碰 3 个以上文件。
- 要改既有产物的名字或结构，比如目录改名、字段改名、章节重排。
- 做完不好回头，比如删文件、批量改名、覆盖已定稿的内容。

不走的情形：改一两处文字、纯问答或查资料、用户已经给出明确步骤。

## 一、摸现状

读相关文件与规范，把这次改动会影响到的地方找齐：要改的文件、会跟着变的文件、依赖它的文件。

会改变结果的疑问先问清再写方案。判据是：同一个问题，两种答法会让你写出的方案不一样，就该问；两种答法方案一样，就自己定，并把假设写进方案。

## 二、写方案

只写一份，落到 `.trae/documents/{名称}_plan.md`，文件名主体用中文，正文与本轮提问用同一种语言。

方案里不写工期、不写时间估计。

## 三、等确认

用当前可用的确认方式请用户过一遍方案。当前环境没有专门的确认工具时，把方案读给用户，问一句是否按此执行。

确认之前，除方案文件本身，不改任何文件、不动任何状态。这条没有例外。

## 四、按方案做

按方案里的步骤顺序执行，做完跑方案里写好的验证动作。

范围或步骤出现实质变化就停下，比如多改了一个模块、换了做法、发现原方案行不通；把变化写进方案，重新请用户确认，不自己扩范围。

## 五、汇报

说清三件事：做了什么、验证结果如何、还剩什么没做。

## 方案模板

```markdown
# {改动名称} 施工方案

## 现状结论
[读到的现状、相关约束、这次改动的影响范围]

## 要改的文件与位置
- `[路径]`：[改什么]

## 步骤
1. [按依赖排序，第几步做什么]

## 依赖与注意
- [依赖的东西、兼容问题、写明的假设]

## 怎么验
- [能直接跑的动作，或能直接看的检查]

## 风险与应对
- [风险]：[怎么防、出问题怎么退]
```

## 交付前自检

逐条查，命中就改：

- 动工前，`git status` 里除方案文件外没有本流程产生的改动。
- 方案六段齐全，没有空段。
- 步骤按依赖排序，后一步不依赖未完成的下一步。
- "怎么验"每行都能照着执行，没有"检查一下"这类没法执行的句子。
- 确认发生在写方案之后、动手之前。
- 方案里没有工期与时间估计。

## 与其它 skill 的分工

| 相邻的 | 边界 |
|:--|:--|
| 需求文档、验收标准、任务队列、独立评审那一套 | 那是更重的流程，归对应工具管；本流程只做一份方案加一次确认 |
| 造 skill 包的 skill（`create-skill`、`pop-shared-skill-create`） | 要改的对象是 skill 包本身时，本流程出施工方案，出包交给它们 |
| 审内容的 skill（`pop-critic-panel`、`pop-review`、`pop-editor`） | 那些审内容质量；本流程管的是改动本身的步骤、风险与验证 |
| 小说管线（`pop-snow-*`、`pop-lantern-*`、`pop-emergent-*`、`pop-outline`、`pop-write`） | 本流程不产小说内容、不碰项目目录规范；小说类大改动由本流程出方案，由对应管线执行 |
| 交付类（`wechat-mp-post`、`visual-image-generator` 等） | 那些产给用户看的成品；本流程产的是给自己用的施工方案 |

## 边界

方案是施工说明，不是需求规格。需求是什么、验收标准怎么定、任务怎么排队、谁来独立评审，不属于本流程。

流程思路参考 Trae 内置 Plan 模式。
