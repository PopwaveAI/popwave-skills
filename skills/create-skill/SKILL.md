# 创建 Skill

将用户描述的任务变成一个职责明确、可以导入 Popwave 的技能。生成文件只是草稿；安装由客户端在用户确认后完成。

## 明确目标

根据对话确认技能解决什么问题、输入是什么、输出是什么，以及会影响结果的约束。信息充分时直接生成；只追问真正影响工作流的缺项，不强迫用户填写固定问卷。不要把一次性示例、你自己的偏好或无关任务写成永久约束。

先阅读 [包规范](references/package-spec.md)。根据任务决定是否需要参考资料、模板或脚本；涉及第三方工具、环境或平台时，阅读 [兼容指南](references/compatibility-guide.md)。

## 生成草稿

客户端会在当前运行指令中提供“本轮技能草稿目录”。只在该目录生成一个技能包，入口直接位于目录下。已有草稿可以继续修改；不要在里面再套一层技能目录，也不要扫描其他对话寻找旧技能。

若未提供草稿目录，说明需要从技能库点击“创建技能”启动受管理的创建流程，或让用户明确指定普通文件输出位置。不要猜测客户端安装目录。

生成 `skill.json` 和 `SKILL.md`，可参考 [入口模板](templates/SKILL.template.md) 与 [清单模板](templates/skill.template.json)。使用模板时填入当前需求的具体内容，不留下占位符。

- 名称、简介用于用户识别和判断使用时机，简介应说明技能能做什么。
- 入口包含适用场景、输入不足时的处理方式、任务流程、输出要求及必要边界。不给无关工作增加规定。
- 明确指向相对路径资源，告诉执行者什么时候读取它们，不把全部资料重复塞进入口。
- 只有重复且确定性的任务才考虑脚本。生成时不执行新脚本、不安装依赖，不把未经执行的代码说成运行验证通过。
- 依赖使用清单声明，不写入真实密钥、个人绝对路径或完整环境配置。
- 至少给出一个正常输入/预期输出示例，以及一个信息不足或不适用时的边界示例。示例服务于实际工作，不要求机械复述格式。

## 自检与交付

检查入口和清单可解析，名称与描述非空，资源引用存在，目录只包含本技能需要的内容；核对是否符合用户目标，是否引入未要求的功能或权限。

回复简要说明：技能名称与用途、生成了哪些文件、声明了哪些依赖、哪些验证确实执行过。引导用户在客户端结果卡片中预览并确认安装。

收到客户端校验错误后，仅根据错误和用户要求修复当前草稿；不要修改客户端索引、校验规则或其他技能。再次生成交由客户端重新校验。除非确实收到安装服务成功结果，不得声称“技能已安装”或要求用户直接写入管理目录。
