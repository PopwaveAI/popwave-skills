# 反馈迭代闭环（feedback-loop）

> 定位：能力 10「反馈与迭代」的落点资产。回答"收到反馈之后，具体改什么、改完记到哪"。
> 原状态：`.learnings/` 只负责**存事实**（角色去哪了、伏笔埋了没），没有"依据反馈改设定"的闭环。本文件补的就是这个闭环。
> 用法：每 5 章节奏报告时执行一次（阶段三）；用户主动提出"不好看/要改"时执行一次。

## 一、三个反馈入口（来源不同，处理方式不同）

| 入口 | 来源 | 特征 | 主要动作 |
|------|------|------|----------|
| **A · 数据** | 用户后台（完读率/追更率/书架比/互动率） | 客观但滞后，且需用户主动提供 | 走 `market-trends.md` 第三节归因表 |
| **B · 主观** | 用户自己的阅读感受 | 最灵敏（读者感受最先出现在作者身上），但表述模糊 | 走第二节的四问定位法 |
| **C · 处置** | 平台通知（拒签/限流/下架） | 后果最重 | 走 `originality-check.md` 第五节应急处理 |

**顺序纪律**：A 与 B 冲突时（数据好但用户说不好看，或反之），**以 A 为准做判断，以 B 为准找线索**——数据不会说谎，但数据不会告诉你哪里难读。

## 二、主观反馈的四问定位法（防止"不好看→瞎改文风"）

用户说"不好看""有点闷""说不清哪里不对"时，**不要立刻改**。先问这四问，把模糊感受定位到具体层：

| 问 | 目的 | 定位到 |
|----|------|--------|
| 1. **是"不想往下看"，还是"看着累"，还是"不代入"？** | 区分钩子问题 / 节奏问题 / 人设问题 | 三选一，走不同修法 |
| 2. **从哪一章开始有这感觉？** | 找起点，避免全改 | 定位到章 |
| 3. **有没有哪个角色或哪段让你出戏？** | 找具体病灶 | 定位到人/场 |
| 4. **如果这是别人写的，你会建议他怎么改？** | 借用户的判断力，避免 AI 猜 | 得到方向 |

**三类的对应修法**：

| 感受 | 最可能是 | 修法 | 不要做 |
|------|----------|------|--------|
| 不想往下看 | 钩子弱 / 爽点兑现慢 | 提高章末钩子强度、提前爽点（`hook-techniques.md`） | 不要加悬念密度（堆钩子会累） |
| 看着累 | 信息密度高 / 段落长 / 世界观解释多 | 通俗化处理（`revision-methods.md` 第四节）、拆长段 | 不要删情节（删了会更空） |
| 不代入 | 人设薄 / 主角被动 / 情绪没演出来 | 回改 `01-人物档案.md` 的动机与矛盾维度；检查主角本章有没有"主动做选择" | 不要加内心独白（独白是最糟的代入手段） |

## 三、闭环四步（收集 → 归因 → 动作 → 沉淀）

```
① 收集：拿到数据 + 主观感受（每 5 章一次）
      ↓
② 归因：数据走 market-trends 第三节表；主观走上面四问
      ↓  产出："问题在 X 层"
③ 动作：一次只改一层（改两层就分不清是哪层的功劳）
      ↓  产出：改了大纲 / 人物 / 节奏 / 文风 中的一项
④ 沉淀：按第四节表写进对应文件 ← 这一步最常被跳过，也是最值钱的
```

### 动作层的四个旋钮（按代价从低到高）

| 旋钮 | 改动范围 | 何时用 |
|------|----------|--------|
| **钩子调整** | 只改章末 | 追更率低但完读正常 |
| **节奏调整** | 改情绪单元的划分（`02-情绪曲线.md`） | 完读率整体偏低 |
| **人设调整** | 改 `01-人物档案.md` 的动机/矛盾 | 评论点名某角色 |
| **结构回改** | 回 1.3 改故事结构 | 前三个旋钮都试过仍无效——骨架错了。**这一条要慎重，改结构等于返工，但比打补丁正确** |

> 硬规则（沿用 1.3.5）：用户在摘要阶段提出方向调整 → **回 1.3 改故事结构**，不要在人物与章节层打补丁。骨架错了，补丁越多越乱。

## 四、沉淀去向表（哪类结论写哪里）

| 结论类型 | 写入位置 | 格式要求 |
|----------|----------|----------|
| 单章出现的问题 | `.learnings/ERRORS.md` | 问题 + 原因 + 修法 + 章号 |
| 角色状态/关系变化 | `.learnings/CHARACTERS.md` | 与既有记录合并，不留矛盾 |
| 情节推进与伏笔 | `.learnings/PLOT_POINTS.md` | 标记"已回收/未回收" |
| **有数据支撑的写法规律** | `references/my-methodology.md` 第五节「已验证经验」 | **必须注明书名 + 数据 + 对应改动**。无数据佐证的推测不写（该节只收数据结论） |
| 节奏模板的调整 | `02-情绪曲线.md` | 说明为何偏离原模板 |
| 用户的方向决策 | `00-大纲.md`「作者决策」区 | 记原话依据，便于后续回看 |
| **本技能自身的缺陷** | 技能目录 `prd/进度与待探索.md` | 这条最容易被漏——**用技能时发现技能不好用，要回写技能，不是只在项目里绕过去** |

## 五、节奏与频次

| 时点 | 动作 | 产出 |
|------|------|------|
| 每章 | 写后处理（3.4）+ 记忆更新 | 章节文件 + `.learnings` |
| **每 5 章** | **节奏报告**：跑 `chapter_stats.py --all` 汇总 + 询问用户后台数据 + 按本文件归因 | 报告 + 动作项 + 沉淀记录 |
| 每卷末 | 完整 9 维审查 + 伏笔回收盘点 | 卷级复盘 |
| 完结 | 全书复盘：哪层问题反复出现 | 写进 `my-methodology.md`，供下一本用 |

## 六、防偏三条（反馈最容易把人带沟里）

1. **不被单条评论带偏**。一条激烈评论可能来自一个非目标读者。看重复出现的词（≥3 次）才当信号。
2. **不为数据牺牲立意**。数据能告诉你节奏慢了，不能告诉你该写什么。核心立意（`00-大纲.md`）不因数据改动。
3. **不在验证期/首秀期改前 3 章与书名封面**。反馈要改也记下来，过了窗口期再动（见 `market-trends.md` 第五节红线）。
