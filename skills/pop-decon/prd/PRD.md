# PRD · pop-decon（拆书专家入口）

## 解决什么问题（带凭据）

拆书是一个多步流水线，需要一个不常驻的入口做编排：下载源文件、分章归一、确定拆解范围、路由到主拆解、沉淀成品。此前入口在「分章」处断链——`pop-decon-dimension` 的 L1 要求读 `_temp/chapters/chXXX.txt`，但全仓无代码生成（`tool-split-chapters` 补上之前）。入口的 Step 1 也只靠对话征询范围，无法被独立交互（宿主）驱动。

## 解决思路（每步为什么必须这样）

1. **入口只编排，不拆解**。下载、分章、征询、路由、沉淀都是交互编排环节，没有子 agent 适配点；真正拆解路由给 `pop-decon-dimension`。入口常驻会占用调度，所以声明「不常驻调度」。
2. **分章在 Step 0 完成**。范围征询（Step 1）需要章清单才能让用户或宿主选范围，分章是征询的前提，所以排在 Step 0。
3. **Step 1 读配置优先于征询**。独立交互（宿主）已冻结的 `拆解配置.json` 直接消费，跳过对话征询；没有配置时保留对话征询兜底。这样同一入口同时服务「对话路径」和「宿主驱动路径」。
4. **范围与配置一起传给 dimension**。范围（硬约束）进配置字段，重点方向（软偏好）进 `focusDimensions`，dimension 据此决定 L2 呈现，不裁剪 L1。

## 关键取舍

| 选了什么 | 放弃了什么 | 为什么 |
|:--|:--|:--|
| 入口保留对话征询兜底 | 不做成纯配置驱动 | 对话路径（无宿主）仍需入口自己征询，砍掉兜底会让对话拆书不可用 |
| `focusDimensions` 只影响 L2 | 不让用户裁剪 L1 八维 | L1 八维是门禁第 3 项的前提，裁剪会连带拖垮锚点池与证据密度（见 dimension PRD） |
| 分章路由 tool-split-chapters | 入口不内置分章逻辑 | 分章是确定性脚本，归 `scripts/`，入口只路由，避免双实现 |

## 不做什么

- 不拆解、不提取八维、不产出六模块（`pop-decon-dimension` 的活）。
- 不分章（`tool-split-chapters` 的活）。
- 不下载（`tool-download-webnovel` 的活）。
- 不做原子候选归集与入库（dimension Step 8 的活）。
