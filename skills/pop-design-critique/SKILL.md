# pop-design-critique

> 对页面截图或运行中的界面做结构化评审：每条必须落到「位置 → 问题 → 影响」，按可用性、视觉层次、一致性、可读性四维出报告。v1.0.0：初始版。完整版本历史见 [CHANGELOG.md](CHANGELOG.md)。

## 这个 Skill 做什么

**做**：拿到页面截图（或运行中的地址）＋ 页面目标，出评审报告，指出哪块该改、为什么。只审不改。
**不做**：不改代码、不写替代方案、不打分、不排名。
**产物**：`审查/设计评审-{页面名}-{YYYYMMDD}.md`，外加对话里三条最痛的问题。
**下游消费者**：做改动的人。评审结论不自动变成改动，改不改由用户拍板。

**是审稿，不是验收**：截图只能审静态视觉。交互、滚动、响应式、键盘可达、加载态必须实机验证，本 skill 判不了——这也是本 skill 最容易越界的地方。

## 怎么操作

### Step 1 收材料（缺目标就停）

三样必需，缺一件就问一句，不追问其他：

| 材料 | 为什么必需 | 缺了怎么办 |
|:--|:--|:--|
| 页面截图（整页，含首屏与折叠以下） | 评审对象本身 | 让用户补，或给运行地址自己截 |
| 页面目标一句话：用户在这一页要完成什么 | 没有目标只能评「好不好看」 | **必问，只问一句** |
| 阶段：早期方案 / 交付页 | 决定审多细（见 Step 2） | 按交付页处理 |

选填：设计 token、组件库、同类页面截图（一致性基准）。不提供时，一致性维度只报「存疑」，不凭感觉断言。

### Step 2 定阶段的审查范围

| 阶段 | 只审 | 不审 |
|:--|:--|:--|
| 早期方案 | 信息架构、主次层级、流程能不能走通、每块有没有存在的理由 | 像素对齐、间距一致性、字号细节 |
| 交付页 | 上面全部，加对齐间距、对比度、文案、空/加载/错误状态、移动端首屏高度 | — |

早期就拿像素级问题压人，会把人带去做装修而不是修结构。这是本 skill 的第一条阶段纪律。

### Step 3 按四维审

逐维过一遍，每维找**具体位置**，不写整体印象：

1. **可用性**：用户的目标能不能在这一页完成。主操作是否唯一且可找到；有没有让用户迟疑的并列选项；该有的入口有没有缺、不该有的入口有没有挤占注意力。
2. **视觉层次**：视线第一落点是不是用户最该先看到的东西；同级元素是否同权重；强调手段（大小／颜色／位置／留白）是否只有一种在起作用；有没有三个以上元素同时在喊。
3. **一致性**：同类元素在不同位置是否长得一样（按钮高度、圆角、间距节奏、图标风格、文案语气）；有没有新造一套和现有 token 打架的样式。无设计真源时此维度降级为「存疑」。
4. **可读性**：正文行宽、行高、对比度、信息密度；标签和数字里有没有省略号截断关键信息；长内容是不是塞进了不滚动的容器。

另查一条本项目的习惯：**每个元素是否服务明确的用户目的**。口号式文案、装饰性图形、重复信息、层层嵌套的卡片都算问题，归入「视觉层次」。

### Step 4 写条目：位置 → 问题 → 影响

每条三段，缺一段不算条目：

```
位置：{页面名}左上角搜索框右侧的筛选按钮
问题：和主按钮同色同尺寸，两个都像主操作
影响：第一次进来的用户不知道先点哪个，选错会多走一步
```

- **位置**：写到别人不看页面也能找到。「顶部」「下面那块」不算位置。
- **问题**：描述看到的事实，不写感受。「不够好看」不是问题，「主次按钮同权重」是。
- **影响**：写用户会怎样，不写「影响体验」。写「会多看两秒」「会误点」「会以为没有这个功能」。

### Step 5 定级排序

| 级别 | 判据 |
|:--|:--|
| 🔴 阻断 | 用户完不成这页的目标，或完成要走错路 |
| 🟡 干扰 | 能完成，但会迟疑、误点、多看 |
| 🔵 打磨 | 不影响完成，属于一致性或精致度 |

按 🔴 → 🟡 → 🔵 排，总数上限 10 条，不凑数。同一原因导致的多处同款问题合并成一条，位置写成「X、Y、Z 三处」。

### Step 6 交付

报告落到 `审查/设计评审-{页面名}-{YYYYMMDD}.md`，模板：

```markdown
# 设计评审·{页面名}·{YYYYMMDD}
> 阶段：{早期/交付}｜页面目标：{一句话}｜材料：{截图/地址}｜未验证：交互、滚动、响应式、键盘可达

## 裁决
🔴阻断 N｜🟡干扰 N｜🔵打磨 N｜存疑 N

## 阻断
1. 位置：…｜问题：…｜影响：…

## 干扰

## 打磨

## 存疑
（缺设计真源、或只能在真机上判断的，写明要补什么才能裁定）
```

对话里只讲 🔴 与 🟡 的前几条，其余指向文件。不追问「要不要我改」。

## 红线

1. **读取协议**：读 skill 文件与设计文档用 `Get-Content -Encoding UTF8 -Raw`，不用 Read 工具（会截断丢内容）；读截图用 Read。
2. **没有页面目标不开审**：先问一句「用户在这一页要完成什么」，拿到再动手。没有目标的评审只能产出「好不好看」。
3. **每条必须带位置**：给不出位置的删掉，不进报告。
4. **只审不改**：不写替代方案、不贴代码、不改文件；修改方向一句话即可。
5. **交互项不越界**：截图审不了的（滚动、响应式、键盘、加载态）写进「未验证」，不许当已通过。
6. **一致性要有真源**：没给 token 或同类页面基准时，一致性维度只报存疑，不凭感觉断言。

## 执行模式

主 agent 直接执行，不派子 agent。评审看的是同一批截图，多 agent 重复看图不增信息；需要多视野挑刺时用 `pop-critic-panel`，那里处理的是文本靶子。
