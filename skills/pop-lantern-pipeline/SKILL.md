### 开工前须完成的检查（贯穿本技能与全流程）

开工前与定稿前各执行一次，自查三问：本产出若要更好，尚缺哪些未见过的候选面？当前信息是否充足？是否存在未探索的更优选项？

- **一、先找出缺口。** 将"若要更好还须见过哪些面"明确列出，再列出已覆盖项，二者之差即为缺口。缺口内只要尚有一个维度未覆盖，即须取材。取材成功即采用；取材失败，不得勉强成文。
- **二、缺口足够时方可取材。** 检索项自拟。来源优先使用内部 wiki 站 **https://wiki.popwave.cn**，不足时再补充网络检索。单个环节最多取材一轮，一轮最多提出五个检索项，单次回传不超过 30KB；超出上限即截断，仅保留结论。
- **三、交付候选须附依据。** 以本技能的判断尺，将现有项与候选项并列制成打分表，不得以一句"这样更好"一笔带过。只能交付候选或升级版，最终选定不由本环节决定。
- **四、交付后复检。** 产出或候选交付后，自查"这是否已是上限、是否有更优候选"。确有更优者方可升级重议，上限两轮。

取材内容仅进入上下文，仅当升级被采纳后方可写入产出。

## 职责范围

| 职责 | 说明 |
|:--|:--|
| 一次性安装（fresh） | 创建目录，写入 `状态.md`（精简状态文件），按需导出展示面板与 README |
| 一次性导入/续写（import/resume） | 依次执行资产扫描、文件归位、缺口分析、落地 Phase 判定、状态重建、补跑调度 |
| 状态文件维护 | `状态.md` 为唯一状态总账，agent 只读写其中的状态片段；`项目总控.html` 是仅供老板查看的展示面板，按需导出，**agent 不读取 html** |
| **内容库体系索引** | 内容库分散归各环节包持有：plot 持有剧情-情绪打分表与单元剧模板库，outline 持有套路库，stage 持有力量体系模板库与世界观模板库。pipeline 只维护统一索引表与消费纪律，不持有库文件 |

**日常路由不经本技能**：用户说"继续写""下一步""写正文""审核"时，主 agent 按专家提示词的阶段地图直接选定 skill，先读取 `状态.md` 取得状态片段（mode/phase/current_unit/current_chapter/就绪态），路由参照下方「单元剧循环状态机」。pipeline 不写正文，不做内容转换，不常驻。

**执行方式**：由主 agent 直接执行。初始化与导入交互（资产清点、缺口确认、落地决策）由主 agent 完成；生成任务由主 agent 加载对应子 skill 执行。不得派发子 agent 执行 skill 生成任务。

## 内容库体系（灯塔流 v3 核心）

**本管线的做法**：agent 不凭空创造内容，而是从库中择取配方，换皮适配。LLM 凭空生成只能得到平均质量的网文；采用经真小说抽离并验证过的配方再适配，质量下限被拉高。这是 AI 写小说完整运行的底层方法。

> **内容库模板不足时的硬性规定（2026-09-11 老板拍板）**：当前内容库各库多为占位与示范，回填不足，**各环节不得假设"库里有配方"**。对应库没有匹配配方时，必须走 research 现场提取或定向补采（各环节 SKILL.md 的取材检查均为硬性，见下），不得跳过取材凭感觉硬写。

### 统一库规（每库头部一致，新增条目照此写）

```
- 名称：{配方名}
- 内核：{可复用的核心结构/机制，3-5句}
- 来源：{哪本书/哪类作品抽离}
- 验证状态：{头部作品/普通验证/待验证}
- 适配规则：{什么题材能用/怎么换皮}
- 不可动硬核：{哪些部分禁止改}
```

### 消费纪律（全管线统一）

1. **先查库，再创造**：对应环节开工前必须查对应库。库中有配方时，择取配方换皮适配；库中没有时，现场提取（由 research 聚焦调研查实），并在 **48 小时内回填**，标注"待验证"。
2. **一个主配方加微调，不得多配方硬拼**：只择取一个主配方，其余只能作配料。拼接两个主配方必定串味。
3. **适配不改内核**：换皮只改动名称、场景、题材外壳；"不可动硬核"字段不得改动。
4. **回填验证**：review 记录"哪套配方生效、效果如何"，对应库同步更新验证状态。
5. **跨项目资产**：内容库按库归持有环节包管理，谁持有谁负责回填验证；任何灯塔流项目均可跨包消费。回填时注明提取自哪个项目（书名或项目名）。

### 剧情-情绪打分表特殊地位（审美固定位）

情绪刻度以 `{pop-lantern-plot}/references/内容库/剧情-情绪打分表.md`（plot 包）为**唯一权威参照**，不得另立刻度。**引用纪律（2026-09-11 老板拍板）：本文件不复制打分表内容**（情绪清单、8 分示例、铺垫规则），需要时打开打分表查级：第二节情绪模块（基础五情主推、高阶慎赌）、第三节分数档位（铺垫成本为硬性约束）、第四节情绪细则（"铺垫至引爆"的剧情落点）、第五节峰值规则、第六节反例区。标注格式为 `{情绪}·{分值}`（可并列）。**同源声明**：打分表与 `pop-outline/references/剧情-情绪打分表.md` 同源，结构、示例与规则一致；**同源同步是打分表本身的事**，本文件只索引不持有。

## 怎么操作（规程全内联）

### Step 0：导入/续写模式

> 触发条件（满足任一）：一、用户说"导入""续写""已有""接续""迁移"；二、执行 Step 1 初始化时检测到 `正文/` 或 `设计库/` 已有文件；三、项目目录已有内容但无 `状态.md`。
> 理念：pipeline 只做调度，不做内容生产。本环节只负责资产清点、文件归位、缺口分析、补跑调度；深度内容转换（正文反推、设计补建）由主 agent 加载对应 skill 完成。

| `skill-generated` | 对应skill正向产出 | 正常消费 |

**0c 缺口分析**：归位完成后对照依赖链逐位检查。就绪判定为文件存在，查文件系统：

| 位 | 就绪判定 |
|:--|:--|
| 1 | `立项/00-融合立项稿14维.md`（旧版三件 01/02/03 齐也可，调度 seed 转写） |
| 1a | `调研采风/采风/` 世界观-*.md 与 人物-*.md（立项前置采风，seed 后必跑） |
| 2 | `设计库/` 五长档：世界画像、世界法则、位阶-社会坐标谱、世界格局、基调母题（类型风味基线随首喷），以及 `人物库/` 两档：主角、角色库 |
| 3 | `剧情库/00-主线结构表.md` |
| 4 | `剧情库/单元N-编排.md`（N=当前单元号） |
| 5 | `章纲/ch{NNN}-章纲.md`（NNN=下一章待写；单元1前3章章纲含开篇三要素与爽点标注） |
| 6 | `正文/ch*.txt`（current_chapter=最大编号+1） |

进度检测：`正文/` 有文件时，提取最大章节号，current_chapter 取下一章待写章号；单元号取 `剧情库/` 与 `设计库/舞台/` 中的最大单元号，无则为 1。质量来源检测：user-original 与 pipeline-relocated 标 ⚠️需校验；skill-generated 标 ✅。最终输出缺口报告。

**0d 落地 Phase 决策**（依据缺口报告与正文进度）：

| 条件 | mode | 落地位 | 说明 |
|:--|:--|:--|:--|
| 正文有、章日志有、全书日志有 | resume | 5 或 6 | 状态完整：下一章章纲已拼接时取 6，未拼接时取 5 |
| 正文有、账本缺（章日志或全书日志） | resume | 先由 0f 调度 review reconstruct，再取 5/6 | 需补账本 |
| 正文无、单元编排有 | import | 5（outline） | 缺章纲 |
| 正文无、主线结构表有（首喷完成） | import | 4（plot 单元编排） | 进单元循环 |
| 正文无、融合立项稿有 | import | 2（stage 首喷） | 缺舞台 |
| 全无 | fresh | 1（seed） | 走 Step 1 初始化 |

向用户展示资产清单（含来源标记）、缺口报告、落地 Phase 建议与补跑建议清单（0f），**经用户确认后**进入 0e。

**0e 状态文件重建**：`状态.md` 不存在时，按「状态.md 模板」创建；已存在时用 SearchReplace 更新。字段：mode、phase、current_unit、current_chapter、seed_path（仅路径 C 项目填写）、就绪态按 0c 标 [x]。展示面板为可选项：老板要求时按 `templates/项目总控.html` 填入数值导出。

**0f 调度 skill 补跑**（pipeline 只识别缺口、调度与汇报，不自行做内容转换）：

| 缺口类型 | 调度 skill | 处理内容 |
|:--|:--|:--|
| 有正文、缺章日志或全书日志 | pop-review reconstruct | 批量回溯审核：采样生成逐章章日志与全书日志 |
| 缺立项、舞台、剧情或章纲文档 | 对应 skill（seed/stage/plot/outline） | 读取已有文件，按该 skill 的方法论校验并补全，产出标准格式 |
| 缺前置采风、单元采风或章纲场景料 | pop-snow-research | 按缺口类型定向补采（世界观、人物、剧情、场景），写入 `调研采风/采风/` |
| 已有文档但来源为 user-original | 对应 skill（用户确认后按需） | 校验后标注缺口或确认达标 |

- review reconstruct 采样规则：10 章以内全审；11 至 30 章取最近 5 章，另每 5 章取 1 章；超过 30 章取最近 5 章与第一章，另每 10 章取 1 章。产出 `剧情日志/ch{NNN}.md` 与 `剧情日志/全书日志.md`。
- 设计文档补跑按依赖链顺序执行：stage（设计库五长档：世界画像、世界法则、位阶-社会坐标谱、世界格局、基调母题；人物库两档：主角、角色库），随后 plot（主线结构表、单元编排），最后 outline（章纲）。用户已有正文但缺剧情文档时，由 plot 从正文反推；用户选择跳过 plot 直接续写（降级模式）时，在全书日志手动指定下一章核心事件。
- 不调度的情况：素材层文件由 pipeline 自行按标准分节重组；文风锚定.md 缺失时提示用户执行 pop-dna-style（非 reconstruct 场景）。
- 补跑建议清单：逐文件一行，格式为文件名、来源、状态、建议（正常消费或补跑某 skill）。用户三选：正常接续、按需补跑、全量补跑。

**Step 0 质量检查**：原始资产清单已生成；归位完成（含来源标记）；缺口报告已生成；落地 Phase 经用户确认；`状态.md` 已创建或更新；补跑建议清单已展示。

### Step 1：初始化（fresh 模式）

**前置检测**：执行任何创建动作前先用 LS 扫描。`正文/` 有章节文件，或 `设计库/` 有 .md 文件时，跳转「Step 0 导入/续写」；目录为空或仅有 `状态.md` 时，继续本步。

2. **创建 `状态.md`**：按「状态.md 模板」写入项目根（mode: fresh、phase: init、current_unit: 1、current_chapter: ch000，全部就绪态标 [ ]）；再简建 README.md，含项目信息、目录说明与指向 `状态.md` 的说明。

## 贯穿级·事实优先级裁决顺序（全线统一）

正文、章纲、设定或审查遇到**事实冲突**时，全线（seed、stage、plot、outline、write、review）按以下序列取证，**不得倒序覆盖更高权位的事实**。这是"约束由正文驱动"的落实点：

| 权重 | 事实源 | 说明 |
|:--:|:--|:--|
| 最高 | **用户本轮临时要求** | 可覆盖既有事实，但必须**显式指出其与既有事实的冲突、记录改法**，不静默覆盖 |
| 2 | **已发布正文** | 正文中明确写出的内容，为最高文字权威 |
| 3 | **最新章节事实提取**（章日志） | 正文驱动的最近事实 |
| 4 | **角色卡当前状态** | 关系、能力、伤势、持有物、信息边界 |
| 5 | **世界书/设定规则** | 力量上限、地图、资源、制度 |
| 6 | **活跃伏笔与未解冲突** | 悬着未回收的线 |
| 7 | **大纲** | 剧情库、单元编排、章纲（优先级最低的叙事计划） |

> 裁决原则：叙事计划（大纲）低于已落地事实（正文、章日志、角色卡、世界书、伏笔）；用户临时要求权重最高，但**指出冲突是义务**，即使照办也须让老板与后续环节知道改了什么、为什么改。遇"冲突该以哪条为准"无法确定时，按此表自上而下取证，不做临时拍板。说明：本裁决顺序吸收自 Mirror 09-审查专家的事实优先级 7 级，与全线统一。

## 单元剧循环状态机（4-8，路由参照）

**灯塔流 v3 骨架由三部分组成：遥远目标（北极星，形状级模糊）、舞台（逐步扩展，配方驱动）、单元剧循环（每单元 12 至 20 章，趋向终点）。卷已删除，单元剧是唯一剧情单元与推进节奏，阶段只是主线结构表上的分组标记，不做卷纲。每一环开工前先查对应内容库（见「内容库体系」索引表）与采风库（`调研采风/采风/`）；库或采风库无料时，必须先补跑 research 定向采风再开工（取材检查为硬性，不得凭感觉硬写）。**

### 每章收束（写一章的完整循环，防止路由绕错）

每一章严格按五步循环执行，**outline 写章纲永远在 write 之前，不得跳过**：

```
outline 章纲 → write 正文(ch{NNN}.txt) → review 三件事 → 回到 outline 写 ch{NNN+1} 章纲 → …
```

- **review 三件事**：一、确认本章正文满意，即定稿，未定稿不入库；二、生成 `剧情日志/ch{NNN}.md`（事件源，只增不改）；三、更新 `剧情日志/全书日志.md`（当前态，只记活跃项，replace，回收项写入 `剧情日志/退出档案.md`）。
- **产物的消费方**：review 产出的章日志与全书日志，传给**下一章的 outline** 作为章纲依据，**不直接传给 write**。write 永远跟在章纲之后，不得跳过 outline 直接从日志开写。
- **对应状态机位**：`5(outline) → 6(write) → 7(review) → 回 5(下一章 outline)`；本单元末章 review PASS 后进入 8 剧末回看。

新书流程为 `init → 1(seed) → 2(stage首喷骨架) → 3(plot 主线结构表+单元1编排) → 单元循环`。其中**单元1 前 3 章章纲（5）按开篇三要素排布**：outline 写 ch001 至 ch003 章纲时，按「落差→特权→小账+新标」设计并标注爽点，开篇承诺基线随前 3 章章纲写入全书日志。前 3 章不是空着硬排，也不脱离滚动循环单独执行。前 3 章已写的项目（导入或续写）跳过该设计，只做开篇复盘诊断。单元循环每单元为一轮：

| 位 | 做什么 | skill | 配方库 | 产出 | 完成后进入 |
|:--|:--|:--|:--|:--|:--|
| 3 | 主线结构表（每单元一行：阶段、本集问题、上升维度、剧末钩子） | pop-lantern-plot 任务U | —（对照剧情-情绪打分表（plot 包）定情绪走向） | `剧情库/00-主线结构表.md` | 4（单元1编排） |
| 4+ | 单元级调研与剧情素材实时搜索（**每单元编排前必须执行一轮**：由剧情定向 research 采集冲突升级、转折、解开模型；编排前查 `调研采风/采风/剧情-*`，无对应种子时必补采） | pop-snow-research 场景② | — | `调研采风/采风/剧情-*.md` | 4 |
| 4 | 单元剧编排（择取单元剧类型配方，套用北极星方法武装，四拍标注情绪目标） | pop-lantern-plot 任务E | **单元剧模板库**（plot 包）与剧情-情绪打分表（plot 包） | `剧情库/单元N-编排.md` | 5 |
| 5 | 章纲拼接（剧情-情绪打分表定本章情绪坐标，套路库择取剧情套路，反向设计剧情；每章一文件） | pop-outline | **剧情-情绪打分表**（plot 包）与套路库（outline 包） | `章纲/ch{NNN}-章纲.md` | 6 |
| 6 | 正文写作（每章 2000 至 2500 字） | pop-write | 文风样文库（P0 纯样文原文） | `正文/ch{NNN}.txt` | 7 |
| 7 | 审核与存档（PASS 或 REJECT；含爽点密度、情绪达标检查、配方生效记录） | pop-review | 剧情-情绪打分表（plot 包，达标参照） | `剧情日志/ch{NNN}.md` 与 `剧情日志/全书日志.md` | PASS 后进入 5 或 6 写下一章；REJECT 后回 6 重写本章；本单元末章 PASS 后进入 8 |
| 8 | 剧末回看（单元末章 PASS 后）：一、review 做单元级检查（起承转合、情绪目标兑现）；二、stage 模式C 重跑（沉淀、扩展、防漂移、人物分流）；三、plot 推进上升线（本行画勾，预告下一行）；四、配方生效回填内容库 | 主 agent 调度 review → stage → plot | 各环节包内容库（回填验证状态） | `剧情日志/单元N-回看.md` 与舞台台账增量、主线结构表本行更新 | 回 4（下一单元） |

> **单元1 前 3 章的开篇承诺基线（1+1>2）**：pop-outline 写 ch001 至 ch003 章纲时，把开篇承诺（第 3 章新标、特权信息备忘、对比触发点锚点）随章纲写入全书日志，后续 outline 写章纲时可引用"主角正往那个新标推进"；plot 主线结构表评审"距终点贡献"时，校验开篇立的标是否在预期章节兑现。开篇由此从"只把关一次"升维为"全书承诺基线"。

**单元内滚动**：推荐「4+ 采风 → 4 产出单元 N → 5 拼接单元 N 章纲 → 6 与 7 逐章执行 → 8 剧末回看 → 4+ 采风 → 4 产出单元 N+1」，让后续单元吸收正文成果。

**8 剧末判定**：单元编排预算章数耗尽，且单元三件套（本集问题解决、上升一格兑现、下集钩子立住）完成时，本单元完成，进入 8 回看后开下一单元。

## 设计预期 · 迭代日志 · 下一阶段展望

### 设计预期（站在全管线看）

灯塔流是涌现流的安全版，也是雪花的减法：保留涌现的弹性（只锁根、滚动规划），加上方向约束（方向总表、卷末对手）防止长篇跑丢。相对雪花只砍三处语义——篇幅从"锁死 N 卷"改"量级方向"、卷纲从"一次排完"改"滚动两卷"、review 账本加重（卷末回看＋配方生效回填）。

三条线共用 `pop-outline`、`pop-write`、`pop-review`、`pop-snow-research`；本线与雪花的差别只在规划粒度与状态档回看方式，不该出现在目录与路径上。

本线适合 AI 长连载稳定推进。涌现流试味成功后转灯塔流，路径是"反推方向总表、回填卷1卷纲、设定交接、状态迁移"。

目录按《项目空间目录规范-SOP》11 个一级目录，与雪花一致——本线是三线里目录最先回到规范的一条。

## 存量项目标准化改造（导入与存量项目必跑）

用户导入旧稿，或项目空间命名不标准时跑本节。**它不是可选模式，是导入流程的强制第二步**——实测发现旧项目常只建一份 `状态.md`、目录与文件名一个没动（旧日书项目即如此：`状态.md` 里写着 `mode: import`、`phase: 2f`，命名却是旧的）。

**第一步 认线**：先读 `状态.md` 的线声明与 phase 写法判线（`2a`-`2g` 是雪花流、`4a`-`4e` 是灯塔流、含 `1.5` 是涌现流）；读不出按上游文件判（涌现看 `剧情日志/涌现账本.md`、灯塔看 `剧情库/单元N-编排.md`、雪花看 `剧情库/卷N-卷纲.md`）；仍判不出问用户，不得猜。

**第二步 出差异报告**：按《项目空间目录规范-SOP》第四节映射表逐条比对，列出"哪条移到哪、哪些缺档要补空、哪些对不上"。报告未给用户看过，不得动手。

**第三步 执行改造**：建标准目录；按映射移动并改名；缺失档建空；旧目录搬空后删除；重写 `状态.md`（新编号＋档位状态）。旧项目若本就没有 `状态.md`，这一步等于生成一份新的。

**第四步 出迁移报告**：写 `剧情日志/迁移报告.md`，逐条记改前→改后，另列未匹配项与冲突项。

**红线三条**：只动路径与文件名，不动正文与章日志内容；同名不同源只列出、不自动覆盖；不删原文件（搬空后的空目录例外）。

**三类要人工指认**：`素材/` 拆成采风／下载／沉淀三类靠内容判断，列出交用户指认；`设计/全书设定/` 那批深层档在新架构里无对位，保留原名搬入 `设计库/` 并在报告里标待并入；无对位的目录与散档（`大纲/`、`废弃正文/`、备份目录、`README.md`）原样保留，只登记不搬移。
