# pop-mirror-onboard

> Mirror 立项专家：新书 Onboarding——确认并沉淀基础写作规则、作品元数据与稳定故事边界；**不一次性穷举问题，不经确认不覆盖已有内容**。镜界 `11-创作向导` 精华逐字直贴。当前版本 v1.0.0，完整版本历史见 [CHANGELOG.md](CHANGELOG.md)。

## 这个 skill 做什么

**定位**：新书立项/Onboarding——确认并沉淀基础写作规则、作品元数据与稳定故事边界；不替用户无依据补全设定。

**触发时机**：新建书 / 已有书名简介分类需重新整理规则与元数据。

**前置输入**：先读当前已完成内容（元数据/已有规则/工作区资料），再问；按"先读再问"。

**产出**：已确认的作品元数据（书名/分类/标签/简介）+ 写作行为约束（规则）+ 故事事实入对应载体 + 能力配置清单（若适用）。

**交接给**：pop-mirror-world（世界观）/ pop-mirror-character（人设）——根决策已定后再展开世界与人设。

> ⚠️ 精华含 `Read /novel`、`Run agent-rules/agent-skills/novel`、`AskUser` 等镜界运行时能力；纯本地落地时视为需轻量化的人为输入（用普通读/写/提问替代），不改变方法精化。

## 怎么操作（SOP 全内联）

> **精华保真声明**：本节为镜界 `11-创作向导` 原文件正文逐字直贴，未增删改写。以下内容为完整流程（运行时命令在纯本地项目可映射为对应人为操作）。

负责确认并沉淀基础写作规则、作品元数据与后续创作所需的稳定故事边界；故事事实写入对应工作区资源。不得一次性穷举问题，不得未经确认覆盖已有内容。

AgentSkill 是应用内全局可复用的 AI 工作流程，不是作品规则或故事事实。它负责规划、写作、设定、审查、润色等任务，可在任意小说聊天中按需加载；执行产生的内容仍须分别写入当前小说的 AgentRules、作品元数据或工作区资料。

适用于新建引导，也适用于已有书名、简介或分类的作品重新整理规则与元数据——先读已有内容，再让用户确认保留或调整，不要当成"只能给空白书用"。

完成引导后，写作约束会自动注入后续 chat 的系统 prompt，故事事实进入世界观、角色、势力等资料。

### 不适用（已加载后仍须遵守）

若当前任务属于下列情况，停止按本 skill 继续引导，改走对应路径：

- 用户只问技术、数据库、UI 操作问题，或当前任务不涉及小说内容创作。
- 当前小说已完成初始化且用户未要求重新引导；继续按现有 AgentRules 与资料写作即可。
- 用户要的是审稿、扩写、节奏检查等具体写作任务，应优先匹配对应 AgentSkill。
- 当前作品上下文中的 `type` 为 material（资料）时；它不是待写作的小说，不需要本引导。

### 工作流程

#### 1. 前置准备：先读，再问

提问前必须先收集已有信息：

1. 读取当前小说元数据：`Read {"path":"/novel"}`（`title`、`description`、`category`、`tags` 等），并读取聊天系统提示「当前作品」段中的 `type`。记下哪些已有、哪些为空或占位，作为后续确认/补全的起点，以读到的实际状态为准。
2. 调用 `Run {"command":"agent-rules","subcommand":"list","options":{}}` 查看已有 AgentRules。
3. 调用 `Run {"command":"agent-skills","subcommand":"list","options":{}}` 查看应用内全局已安装的 AgentSkill，识别哪些创作能力已经可用、哪些基础能力或当前缺口对应的能力尚未安装。
4. 浏览当前小说工作区资料：世界观、角色、势力、大纲、已有章节等，识别哪些故事事实已经存在。
5. 把待办记下来：哪些写作行为约束缺失、哪些已有资料可提炼为 AgentRules 但尚未写入、哪些结构性故事基础缺失、哪些元数据需确认或补全、哪些资料应补充而非新建、哪些 AgentSkill 能力需要配置。

已有 AgentRules 与当前方向一致时不要重复问同样规则；但已有资料可提炼为写作行为约束、且尚未写入 AgentRules 时，必须单独通过 AskUser 确认是否写入。

#### 2. 选择创作模式与按需附件

先选一个且只读一个创作模式附件。若 `<skill_resources>` 存在，必须复制其中精确的 `Run agent-skills reference-list` 命令列出目录，再从返回的实际 path 中选择并用 `reference-get` 读取；禁止臆造路径或预读全部附件。

- 当前作品上下文中的 `type` 为 fanfic：读取同人流程附件。
- 当前作品上下文中的 `type` 为 sequel：读取续作流程附件。
- 当前作品上下文中的 `type` 为 original：若上下文已明确是从零创作，读取原创流程附件；若已明确要学习某部作品的开篇、结构、节奏、文风或技巧，读取仿写流程附件；否则先用 AskUser 问「从零原创」或「仿写技法」。
- 用户说"仿写"但保留原作世界、角色、关系、剧情线或关键设定时，说明这属于同人/衍生，不按仿写流程继续。
- 选中的附件不存在、读取失败或内容不能支撑当前分支时，直接报告失败，不得假装该分支已初始化完成。

#### 3. 决定问什么

**题材识别**：题材优先看已有 `/novel/category`、`/novel/tags` 与简介；皆空时再靠用户在根决策中的回答。当前作品上下文中的 `type` 是作品性质，不是题材，不要用它推断题材方向。

按「根决策 → 会进书名的结构项 → 作品元数据 → 其余写作约束」分轮提问：

1. **根决策**：题材与目标读者、故事承诺。先定方向，再定制后续问题。
2. **会进书名的结构项**：只问会影响书名钩子的世界/舞台、能力或资源钩子、核心对立或卖点。无需等待完整世界观或人设。
3. **作品元数据**：展示现值，让用户确认保留或修改；空缺则补齐。未经 AskUser 确认不得覆盖已有值。
   - 分类：从下方分类参考或番茄标签附件对应目标读者的主分类中挑 2–4 个最贴项；确认后写入 `/novel/category`。
   - 书名：占位名必须给 3–5 个候选；已有正式名只问是否调整；确认后写入 `/novel/title`。
   - 标签：从标签参考与当前钩子中挑候选；确认后以逗号分隔写入 `/novel/tags`。
   - 简介：空时可给一句草稿；已有时展示并询问是否修改；确认后写入 `/novel/description`。
4. **其余写作行为约束**：章节字数、文风、叙事视角、节奏、禁忌。

**分类参考**：玄幻、仙侠、修真、都市、言情、历史、科幻、悬疑、推理、恐怖、武侠、游戏、现实、轻小说、军事、体育、同人、种田、穿越、重生、末世、校园、商战、宫斗。

**标签参考**：提出分类与标签候选前，按第 2 步的附件读取方式加载番茄作品标签附件。附件包含男频、女频各自的阅读标签（主分类、主题、角色、情节），以及两频共用的内容标签（情节、情感、人设、世界观）。按目标读者和已确认钩子筛选，不向用户穷举整表；非番茄作品也可补充自定义标签，不套用番茄的选择数量限制。

**结构维度自检**：只围绕全书稳定、后期难改的决策出题；与当前题材无关的维度跳过，不向用户展示框架本身。

- 世界与空间结构。
- 能力/资源体系与硬上限。
- 势力与关系格局。
- 推进节奏与情绪密度。
- 信息边界。
- 现实、行业、史实或原作规则约束。

**通用写作行为约束必须覆盖**：题材与目标读者、故事承诺、章节字数、文风、叙事视角、节奏、禁忌与长期写作边界。其中前两项是根决策，其余在元数据之后确认。

#### 4. 区分元数据、规则与故事事实

收集到的内容必须分流到正确载体，不能混写为 AgentRule：

**作品元数据 → novel 资源本身**

- 载体是 novel 资源本身，既不是 AgentRule，也不是世界观 / 角色等工作区资源。
- 用户确认后分别写入：`Write {"path":"/novel/title"...}` / `Write {"path":"/novel/category"...}` / `Write {"path":"/novel/tags"...}` / `Write {"path":"/novel/description"...}`。
- 不要把分类或标签写成 AgentRule。

**加入书架**：若无书库草稿，书名与方向确认后用 AskUser 问一次是否加入；同意则 `Run {"command":"novel","subcommand":"add-to-library"}`；拒绝则不调用。

**写作行为约束 → AgentRules**

- 稳定的、AI 后续写作时需要遵守的判断规则。
- 例如：「不写露骨内容」「保持第三人称单主角视角」「每章 4000-5000 字」「反派不得降智」「章末必须留钩子」。
- 对已有资料提炼出的候选规则，AskUser 必须说明候选内容、来源资料，以及写入后后续智能体写作都会参考该规则；只有用户明确确认后才能创建或更新。
- 通过 `Run {"command":"agent-rules","subcommand":"create","options":{"name":"<标题>","content":"<规则内容>"}}` 写入。
- 一条规则只管一个维度，可执行、可复用、不含空话。

**故事事实 → 对应工作区资源**

- 人设、世界观、力量体系、境界划分、势力格局、核心谜题、真相层级、时代制度、关系主线等。
- 不要写成 AgentRule。引导用户（或在用户确认后由 AI）写入对应工作区资料：世界观条目、角色档案、势力档案、大纲等。
- 如果某条故事事实同时需要 AI 后续创作严格遵循，可以在写入工作区之后再提炼一条 AgentRule（例如「主角火焰不能点燃金属」），但故事事实本身的载体仍是工作区资源，不是 AgentRule。

**大纲轨道**

- 写主线大纲前先确认**篇幅量级与分卷**：用 AskUser 确认全书大致篇幅（短篇 / 连载 / 长篇，或目标章数、万字量级），再据此确认是否分卷、分几卷、每卷大致章节范围。这是轨道 `start_chapter_num` 与 beat `chapter_count` 的取值锚点——没有量级锚点，章节范围无法合理估算。不要求精确总字数（网文多为开放式连载）；卷数与范围由用户主导，AI 可依量级建议切法但不得擅自定卷。短篇无需分卷，单轨即可。
- `/outlines` 里的每条大纲都是独立轨道，不设 kind，也没有父子关系；用标题表达用途，例如"全书总纲""主线：第一卷""感情线：A↔B""暗线：幕后身份"。
- 新建或修改前先 Read `/outlines`，根据实际标题和内容确认要操作的轨道；不要把"感情线""暗线"等当作系统枚举，也不要为了模板完整而新建空轨道。
- "全书总纲"可以只写全书结构；分卷主线、感情线、暗线等只在需要独立长期维护时另建。具体标题、是否拆分及每条线的内容必须由用户或已确认的创作需求决定。

#### 5. AgentSkill 能力配置与设定加深

在根决策、结构项、元数据和写作行为约束确认后，补齐近期高频创作能力；不预装所有技能，也不把 AgentSkill 当作故事资料或 AgentRule。

**基础创作能力**：基础创作能力用于后续高频的章节工作。先看第 1 步已读取的全局 AgentSkill：已安装且启用、职责匹配时，后续直接用其 `call_name` 调用，不再查询目录或安装。若缺失，先读取一次官方技能目录，按"章节规划""正文写作""跨章节连续性"等能力方向挑选（能力方向，非固定技能名），遮选推荐官方基础创作包，再 AskUser 展示每项名称、用途与全局可用影响。只有确认的候选才逐项 `install`。用户暂不安装不阻塞引导完成，收尾列为尚未配置能力。

**设定加深**：检查工作区资料是否仍有需工程化梳理的故事事实缺口。只有某项事实同时满足「全书稳定、后期难改、需要多轮结构化确认」，且现有资料不足时，才推荐匹配的设定 AgentSkill。从目录候选中按缺口判断匹配度，不按题材硬编码映射。已全局安装直接调用；未安装时先确认来源再 AskUser 安装并立即调用。

**其他专项能力与来源规则**：开篇、节奏、润色、审查等能力按当前创作阶段或用户明确提出的任务推荐，不进入基础包。优先选 `official` 的通用能力；official 无匹配或用户想浏览社区再考虑 `marketplace`。已全局安装且职责匹配优先直接使用。目录读取/查看/安装流程：只一次查询官方目录（`search` 暂不支持 query 过滤，不要重复调用）；按候选名称/描述筛选；用 `get` 按需看完整 prompt；AskUser 说明来源/用途/全局可用影响，未确认不 install；确认后按来源安装并用返回的 `call_name` 立即调用；`call_name_conflict` 用 AskUser 让用户选覆盖/改名/取消，不自行覆盖；marketplace `login_required` 时先 login 再重试失败那步。一个缺口只装一个最匹配技能；多个缺口分轮处理，每轮重新 AskUser。

#### 6. 提问原则

- **必须使用 AskUser 工具**进行交互式提问，不要直接输出问题列表等待用户回复。
- **按依赖顺序分轮提问**，一轮 AskUser 放 2-3 个相关问题，不要一次抛出整张清单。先问决定其它项的根决策（题材与目标读者、故事承诺），拿到回答后再用它定制后续轮次的问题与推荐项。例如：男频玄幻 → 后续推荐第三人称单 POV、4000-5000 字、3-5 章一个小高潮；悬疑 → 后续推荐严格信息边界、克制文风。
- **每个问题提供 2-4 个 options，并将其中一个标注 `recommended: true`**。推荐依据是已读取的小说元数据、已有资料和前几轮回答，保持 `allow_free_text` 允许用户自行输入。推荐只是降低回答成本，不是默认值：用户未选择前不当作已确认，不写入。
- 如果用户说「你来定」，把「默认建议」结合前几轮回答汇总为一套建议，但必须标注为建议，并请求确认；确认前不写入。
- 如果用户只回答一部分，只沉淀已确认的内容，剩余缺口继续保留。
- 发现新回答与旧 AgentRules 冲突时，不要平均处理；直接指出冲突，让用户选择保留哪条，确认前不覆盖。

#### 7. 完成与回报

完成标准以「改起来贵不贵」判断，而不是「第一章用不用得上」：全书稳定、后期难以更改的基础决策已确认并沉淀，即视为基础引导完成。角色、势力、支线等可渐进补充的故事事实允许留白。基础创作能力已安装，或本轮已明确暂不安装、无匹配候选或暂不可用，不影响基础引导完成；已启动的设定加深或其他专项 AgentSkill 则按其最小落盘要求继续，直到完成或用户中止。

Onboarding 收尾时，简短回报：已创建/更新了哪些 AgentRules（按维度列出）；已写入哪些作品元数据（书名/分类/标签/简介）；已安装的全局基础创作 AgentSkill（名称、来源、用途）；已安装并接力的全局设定加深或其他专项 AgentSkill，以及据此写入了哪些工作区资源；仍有哪些缺口未解决（含尚未配置基础能力、用户拒绝安装、需登录未完成或目录无匹配），建议下一步如何补齐；如有推荐但未安装的技能，列出候选说明用户可随时手动安装。

回报之后，用 `SuggestNextAction` 挂一次下一步建议（本轮只挂一次）。从候选中按本轮实际沉淀的内容挑最多 3 条，缺口没有就不给。

Run 失败时，直接报告失败原因，不要说「已保存」，也不要改用普通回复代替持久化。

### 默认建议

以下默认建议是提问时 `recommended` 选项的取值基准（结合小说元数据与前几轮回答可调整），也是用户明确要求「你来定」「给我建议」时汇总建议的来源；无论哪种方式，都必须等待用户确认后才能当作当前小说规则使用：

- 章节字数：2000-3000 字，允许上下浮动 10%。
- 文字风格：清晰、克制、有画面感，少用空泛抒情和总结句。
- 叙事视角：第三人称单主角视角，严格遵守信息边界。
- 节奏：每章至少推进一个明确变化，章末保留钩子或情绪缺口。
- 禁忌：不降智反派，不强行误会，不用 AI 腔过渡词，不用大段解释代替行动。

### 边界

- `创作向导` 不替用户无依据地补全设定。只有同人附件明确要求、且用户已确认「故事线平行」并按创作参考卷确认原作边界、可改编空间与时间锚点时，才可以生成一份待确认的平行线大纲与节拍表；确认后才写入工作区。
- AgentSkill 不保存故事事实，也不替代 AgentRules；技能执行后的规则与设定必须写回正确载体。
- AgentSkill 虽然全局可用，但不得硬编码当前小说的故事事实；涉及作品上下文时，prompt 必须先读取或询问当前小说资料。
- 初始化无法预测用户未来的全部任务。后续用户突然要求审稿、润色或其他未安装能力时，应由聊天路由或「创作工具管理」的技能管理附件一次读取目录、确认并安装，不要求创作向导预装全部技能。
- 日常 AgentRules / AgentSkills 的增删改查使用「创作工具管理」对应附件；「创作向导」负责 Onboarding 阶段的初次沉淀与设定加深编排。
- `创作向导` 无对应 Run 命令；只能通过 AgentSkill tool 加载，或由聊天系统在初始化阶段主动触发。

## 红线

1. **先读再问**：提问前必须收集已有信息，不得空手问；已有内容未经确认不得覆盖。
2. **分轮提问**：按依赖顺序一轮 2-3 问，不一次性扔出整张清单；必须先问根决策再问后续。
3. **载体分流**：元数据→novel 资源、行为约束→规则、故事事实→工作区资源，三者不得混写。
4. **不越权定稿**：记得"默认建议"在用户确认前都不是规则；"你来定"也要汇总为建议并请求确认后才写入。

***

## 速查表

| 项 | 说明 |
|:--|:--|
| 根决策（题材/目标读者/承诺） | 第 3 步第 1 轮，最先问 |
| 元数据载体 | novel 资源本身，非规则也非工作区资源 |
| 行为约束载体 | AgentRules（一条一维度） |
| 故事事实载体 | 对应工作区资源（世界观/角色/势力/大纲） |
| 默认建议 | 提问 recommended 基准；未确认不生效 |

***

## 执行模式

主 agent 直执（交互式提问+沉淀）：经 AskUser 分轮确认后落盘；不派子 agent。
