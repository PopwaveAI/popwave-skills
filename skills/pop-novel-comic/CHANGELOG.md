## v4.3.0 | 2026-08-02

### 翻页阅读器 — 从长滚动 HTML 改为按页呈现

**背景**：用户反馈"不能再继续拼成一个大的 html，应该是按页呈现"。v4.0~v4.2 的 HTML 产出是长滚动页面——所有漫画页垂直堆叠在一个 HTML 中，移动端需要不断向下滑动，不像真实漫画阅读体验。

**核心变化**：HTML 产出从长滚动页面改为**翻页阅读器**——视口内一次只显示一页，点击/滑动/方向键切换，带过渡动画。

**一、排版指南重构** `references/page-layout-guide.md`：

- 新增「HTML 结构规范（翻页阅读器）」章节，替代旧的长滚动 HTML 规范
- 三类页面视图：标题页（data-index=0）→ 漫画页（1~N）→ 章末页（N+1）
- 完整 HTML 模板：含 CSS（全屏沉浸/深色背景/opacity 过渡）+ JavaScript（点击导航/键盘方向键/触摸滑动/页码指示器）
- 导航设计：左侧30%上一页 / 右侧30%下一页 / 中间40%不触发（避免误触）
- 页码指示器：底部居中，标题页和章末页不显示
- `separator` 字段在翻页阅读器中不再渲染（翻页本身就是分隔）

**二、Step 2b 生产步骤更新** `steps/step2b-production.md`：

- §3 标题从"HTML 文字叠加"改为"翻页阅读器 HTML 生成"

- 文字叠加类型表移除"章节标题"行（标题由标题页独立展示）
- 删除旧的长滚动 CSS 代码块（CSS 实现统一在 page-layout-guide.md）
- HTML 生成说明改为翻页阅读器结构（标题页→漫画页→章末页→导航层→交互脚本）
- §4 截图说明适配 `.page-view` 结构

**三、SKILL.md 更新**：

## v4.0.0 | 2026-08-01

### 整体性重构 — 页面级生成架构

**根因分析**：v3.x 架构的根本问题是"像插画集合不像漫画"——每格独立生成一张图，HTML 排列组合，文字在底部遮罩。这种"逐格生成+HTML排版"方案导致：① 格间视觉断裂（每格独立生成，无分格线连续性）；② 布局漂移（50%帧布局被擅自更改）；③ 移动端体验差（格子布局在小屏幕上信息密度过高）；④ 不像漫画（缺少漫画的分格线、格间节奏、页面整体感）。

**核心变化：生成单位从"格"升级为"页"**。Seedream 在单张图内直出完整漫画页（含分格线、多格内容、镜头语言），HTML 仅叠加文字层（旁白条/对白气泡）。画面是 AI 画的，文字是 HTML 叠的——各司其职。

**POC 验证**：通过 8 组 POC 测试验证了 Seedream 直出多格漫画页的可行性——4格网格/6格不对称/竖向条带/8格密集/角色定妆图参考/文字叠加均成功。角色一致性通过定妆图参考（image参数）保持。

**一、页面级生成脚本** 新增 `scripts/generate_comic_page.py`：

- 逐页生成漫画（每页一张含多格的完整图），替代逐格生成
- 支持角色定妆图参考（image参数图生图模式），保持跨页角色一致性
- 格式保真（JPEG magic bytes检测→PNG转码）
- 自动重试（3次指数退避）
- 生成元数据JSON
- 替代旧 `generate_storyboard.py`（逐格生成）

**二、Step 1 导演卡重构** `steps/step1-director.md`：

- **两层推导：故事→页面**。先想清楚"这一话讲什么故事"（故事层），再推导"分几页、每页做什么、每页怎么分格"（页层）
- **起承转合是页面级功能位**。每页承担一个叙事功能（起=建立/承=发展/转=高潮/合=钩子）。高潮剧情可用"大单页"——1页1格全页独占
- **页面设计表**（导演卡核心产出）：页码/功能位/页面类型/格数/格布局/每格内容概述/视觉重心/旁白文字/页间衔接
- **页面类型**：大单页（1格全页独占）/双格对比页（2格）/多格页（3-6格）/竖向连续页（3-4格）
- **格布局方案**：2x2网格/竖向3格/1大2小/2小1大/全页独占/上下双格/左右双格/3x2网格/竖向4格/2大2小
- 删除 v3.x 的分格设计表（布局类/效果类），由页面设计表的格布局替代

**三、Step 2a 页面提示词设计** `steps/step2a-storyboard.md`：

- **页面级提示词**：一个提示词描述一整页（含所有格子），Seedream 一次直出完整漫画页
- **三种页面级提示词模板**：多格页模板（3-6格）/大单页模板（1格全页独占）/双格页模板
- 提示词持久化到 storyboard.md（作为真相源）
- 构图骨架串在每格描述中使用（九种构图手法保留）

**四、Step 2b 页面生成+文字叠加** `steps/step2b-production.md`：

- **逐页生成**（调用 `generate_comic_page.py`，每页带角色定妆图参考）

- **页面配置 JSON**：pages数组配置每页的文字叠加（type/position/text）
- **移动端优先**：页面图片全宽展示，文字叠加使用相对定位，竖向滑动阅读
- 删除 v3.x 的布局一致性校验门禁（无格子布局=无布局漂移风险）

**根因分析**：用户指出"HTML动态化大概率会被搞成为了动态而动态，而不是站在一话的角度上顶层设计"。当前架构中，布局决策在 step2 组装 HTML 时临时做出——选什么布局类、分几页、每页放什么，全部在"画"的阶段才决定，没有叙事依据。布局和故事脱节，导致"为动态而动态"。

解决信息超载导致的剧情看不懂问题——不是叙事结构问题，而是篇幅不够。

**根因分析**：玄鉴仙族第1话将2章原文（ch1122+ch1395）塞进12格漫画，信息负载超载2-3倍：

|:-----|:----------|:------------|:--------|
| 原文章节 | 2章 | 1章 | 2x |

| 场景数 | 7个 | 2-3个 | 2.3-3.5x |
| 定妆角色 | 7个 | 3-5个 | 1.4-2.3x |
| 故事线 | 2条 | 1主+0-1副 | 2x |

v2.9.0 解决的是"给定篇幅内怎么讲好故事"，v2.9.1 解决"篇幅本身够不够"——这是更上游的决策。

**一、话数规划**（`step1-director.md` 新增 §2.5）：

改编分析前先评估信息负载，四项指标：

| 指标 | 统计方式 |
|:-----|:---------|
| 关键信息数 | 初步提取"丢了看不懂后续"的信息点 |
| 场景数 | 统计不同地点/时间的场景切换 |
| 出场角色数 | 统计有名字且说话/行动的角色 |
| 故事线数 | 统计独立并行的主要情节线 |

负载分级与话数决策：

| 总负载 | 判定条件 | 话数决策 |
|:------|:--------|:--------|
| 轻 | ≤5信息+≤3场景+≤4角色+1故事线 | 1话（6-8格） |
| 中 | 6-8信息+4-5场景+5-6角色+1-2故事线 | 1话精选（8-12格） |
| 重 | ≥9信息+≥6场景+≥7角色+≥2故事线 | **拆分为2+话** |

**拆分触发线**：四项指标中任意两项达到"重"级别 → 拆分。

**二、拆分原则**：

1. **按故事线切**：不同 POV/地点的并行线各自独立成话
2. **按因果断裂点切**：找到"起因→发展"或"发展→决策"之间的自然停顿
3. **每话有完整弧线**：起因→发展→决策→后果，不能只有"上半场"
4. **保留钩子衔接**：前一话的结尾钩子指向后一话的开头

拆分后每话独立走完整 Step 1 → Step 2 → Step 3 流程。

### 叙事主线设计 + 名场面设计方法论

解决两个叙事质量问题：漫画剧情看不懂（信息碎片化、无因果链），以及名场面张力不足（关键帧全是 talking head，缺乏视觉冲击力）。

**根因分析**：玄鉴仙族第1话测试中，导演卡的9条关键信息平铺直叙塞进12格——信息覆盖了但读者看到的是碎片不是故事；关键帧（金瞳定策/剑意冲霄/伐蜀只是顺便）全是角色站着说话的 talking head，去掉对白后画面没有任何视觉信息。

**一、叙事主线设计**（`step1-director.md` 新增 §1.5）：

信息审计是"零件清单"，叙事主线是"装配图"。先设计装配图，再清点零件：

1. **一句话故事**：读者看完本章后应该能用一句话总结什么？`{谁}在{什么情境}下做了{什么决策/行动}，导致了{什么后果}`
2. **因果链设计**：起因（1-2帧）→ 发展（2-3帧）→ 决策（1-2帧）→ 后果（1帧）。每帧必须推进故事，不是呈现信息
3. **主副线结构**：A-story 占 60-70% 享最佳帧位，B-story 占 20-30% 必须服务 A-story（铺垫/对比/悬念），无关系的副线砍掉
4. **读者理解路径**：模拟没读过原文的读者，逐帧列出"理解了什么"和"期待什么"——空白帧=废帧

**二、信息分级**（`step1-director.md` §3 关键信息审计升级）：

不是所有关键信息都同等重要，按优先级分三级：

| 级别 | 定义 | 处理 | 帧位 |
|:-----|:-----|:-----|:-----|
| S 级 | 丢了完全看不懂主线 | 必须呈现，分配最佳帧位 | 独占格/名场面 |
| A 级 | 丢了影响理解但不致命 | 应该呈现，可旁白浓缩 | 正常帧 |
| B 级 | 世界观增色但不影响主线 | 可砍，帧位紧张时第一个砍 | 合并或旁白 |

S 级不超过 3 条——一章的核心决策/转折最多 2-3 个。审计表新增"优先级"列。

**三、名场面设计**（`references/storyboard-guide.md` 新增 §8）：

高光独占格解决"信息不稀释"，名场面设计解决"画面有没有冲击力"：

1. **名场面识别三标准**：视觉奇观（画出来好不好看）/ 情绪爆发（能不能让读者感到什么）/ 剧情转折（是否改变故事走向）。三条满足两条 = 名场面，必须用最大布局 + 高精度提示词。每章至少 1 个
2. **张力构建五技法**：尺度对比（角色渺小vs环境宏大）/ 静默铺垫（爆发前留一格安静的）/ 反应镜头（不画事件画反应）/ 视觉隐喻（用象征物承载情绪）/ 留白截断（关键时刻画面截断）
3. **冲击帧提示词升级**：普通帧写"发生了什么"，冲击帧写"后果和感受"。不写"剑意冲霄"，写"百丈山峰被剑气切出裂痕，碎石纷飞如暴雨"
4. **talking head 反模式**：角色站着说话、去掉对白后画面什么都没有 = 最差漫画画面。名场面的画面应该不需要对白也能传达信息

- 导演卡模板新增「叙事主线」段落

- **根因**：popwave webview 安全策略禁止加载外部资源（相对路径、绝对路径、file:// 协议均被阻止），HTML 中 `<img src="output/frame1.png">` 在 popwave 中显示为图片损坏
- **验证过程**：相对路径 ❌ → 绝对路径 file:// ❌ → base64 内联 472KB ✅ → base64 内联 6.5MB ❌（文件过大无法打开）→ 压缩 base64 内联 ✅
- **修复**：新增 `scripts/inline_html.py` 脚本，将 HTML 中所有本地图片引用压缩为 base64 data URI（默认 800px 宽 + JPEG quality 65），使 HTML 完全自包含
- **新增铁律6**：HTML 必须内联图片，禁止交付含外部图片路径的 HTML
- **step2-generate.md** 新增 §4 HTML 图片内联化步骤（必须执行）和质量检查项

## v1.1.0 | 2026-07-29

### 修复（格式保真）
- **根因**：Seedream API 返回的 URL 资源实际为 JPEG（magic bytes `FF D8 FF`），但 `generate_storyboard.py` 以 `.png` 命名保存，导致扩展名与实际格式不符
- **现象**：浏览器做 MIME sniffing 能兼容显示，但 popwave webview（nosniff 模式）按扩展名校验 MIME，判定为图片损坏
- **修复**：新增 `ensure_png_format()` 函数，在图片下载后自动检测 magic bytes，若为 JPEG 内容则用 Pillow 转码为真 PNG
- **同步修复**：`pop-novel-visual/scripts/generate.py` 的 `download_file` 和 `save_base64_image` 两条路径（新增 `ensure_format_integrity()` 函数）
- **新增铁律5**：下载后格式保真
