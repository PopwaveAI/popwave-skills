# pop-shared-skill-create

> Popwave Skill 设计规范——告诉 agent skill 该写成什么样、按什么顺序写入文件。v8.0.0：全文用词升级为 Mirror 创作专家标准（行为指令/是A不是B/锚点判断/行业词直用），新增「五、用词与表达」。完整版本历史见 [CHANGELOG.md](CHANGELOG.md)。

## 这个 Skill 做什么

用于创建、改造、修复 Popwave Skill。产出不是泛泛建议，而是可直接写入的文件：`SKILL.md`（主文档）、`skill.json`、`CHANGELOG.md`，按需还有 `references/`、`templates/`、`scripts/`。

它是什么，不是什么：

- 它是规范：告诉 agent skill 该写成什么样、按什么顺序写入文件。
- 它不是创作方法论：写小说的方法进各业务 skill 的 `references/`，不写进本规范。
- 它不是编辑器：本 skill 不提供命令，agent 读规范后自己动手。

## 怎么运作

1. **确认职责**：确认 skill 名称、触发场景、核心产物、下游消费者。用户已给 PRD 或现有 skill 时，直接以它为源材料。
2. **提取主干**：做"换皮测试"——抽掉具体项目名后仍能复用的流程才写进 skill；一次性案例或纯资料查询不强行 skill 化。
3. **规划结构**：`SKILL.md` 一个文件装下完整 SOP（执行要点内联），方法论进 `references/`，可复制产物进 `templates/`，可执行代码进 `scripts/`。
4. **动手写文件**：写 `SKILL.md` + `skill.json` + `CHANGELOG.md`，按需创建一级资源目录。改造旧 skill 时只改结构、格式、用词、检查条件，不擅自改业务方法论。
5. **一致性校验**：检查 description 触发条件、版本三处一致、速查表覆盖全文件、弱保障文件都有读取时机，涉及代码时验证 `scripts/` 的代表性脚本可运行。

**执行模式**：主 agent 直执（规范理解与写文件一体，无自然子 agent 适配点）。

## ❌ 质量红线

| # | 红线 |
|:-:|:-----|
| ❌1 | **读取 skill 文件禁止用 Read 工具** — 用 `skill_view` 或 `Get-Content -Encoding UTF8 -Raw`；Read 有行数限制会截断丢内容 |
| ❌2 | **创建必须双文件** — SKILL.md + skill.json 缺一不可，缺一个平台无法注册 |
| ❌3 | **SKILL.md 必须一个文件装下完整流程** — SOP 主干+各步执行要点+红线全在 SKILL.md 内；禁止 steps 目录（新建不建，改造时合入删目录清引用）；即使 references/ 没被读到，agent 也要知道完整流程 |
| ❌4 | **版本三处一致** — SKILL.md 正文 + skill.json + CHANGELOG.md 版本号必须一致 |
| ❌5 | **代码必须进一级 `scripts/`** — 可执行脚本、工具代码、批处理逻辑不放在 references/templates 根下 |
| ❌6 | **红线≤7条** — 只有违反后会断裂下游的才算红线；格式细节降级为检查清单 |
| ❌7 | **SKILL.md 禁止堆版本历史块** — 摘要只写当前版本一句+CHANGELOG 指针；历次变更一律进 CHANGELOG.md |

## 一、格式规范

- **frontmatter ≤ 4 行**，只留 name + description；version/tags/category/dependencies 全移入 skill.json 或正文。
- **正文标题下 `> 摘要`** 只写当前版本一句 + CHANGELOG 指针。写法：`> {一句职责}。vX.Y.Z：{当前版本改动简述}。完整版本历史见 CHANGELOG.md`。description 已承担定位与触发，摘要不重复定位，也不堆历次版本变更。
- **description 必须含触发条件**（"当用户说…时启用"），说明做什么+何时触发+产出给谁。
  - 差：`"用户调研工具"`（没说何时用、产出给谁）
  - 好：`"当用户说'调研'时启用。产出调研报告供给下游管线。"`
- **skill.json 七字段**：`id`（与目录名一致）/`version`（与 SKILL.md+CHANGELOG 一致）/`displayName`/`description`/`entry`（固定 `"SKILL.md"`）/`activation.slashCommands`/`permissions`：

```json
{
  "id": "my-skill",
  "version": "1.0.0",
  "displayName": "我的技能",
  "description": "当用户说'做X'时启用。产出供给下游管线。",
  "entry": "SKILL.md",
  "activation": { "slashCommands": ["my-skill"] },
  "permissions": { "readProjectFiles": true, "writeProjectFiles": true }
}
```

## 二、内容定位：一个文件装全部 + 三类资源

```
my-skill/
├── SKILL.md          ← 主文档：SOP主干（执行要点内联）+红线+速查表+版本
├── skill.json        ← 机器读：平台注册用
├── CHANGELOG.md      ← 变更历史
├── references/       ← 知识层：读后理解（方法论、规范）
├── templates/        ← 模板层：复制填充（空模板）
└── scripts/          ← 代码层：可执行脚本、批处理逻辑
```

**单文件自包含，是什么、不是什么**：SKILL.md 一个文件装下完整流程，不是只写个目录让 agent 去翻别的文件。为什么这么定：实测运行环境只注入 SKILL.md 全文，对 step 文件的引用形同虚设。全仓 41 个 skill 的 steps 目录已于 2026-08-24 全部合入单文件。

| 目录 | 定位 | 使用方式 | 典型文件 |
|:-----|:-----|:---------|:---------|
| `references/` | 知识层 — 读后理解 | 阅读理解，指导操作 | 搜索SOP、调用规范 |
| `templates/` | 模板层 — 复制填充 | 复制→填充→产出文件 | 空白模板、输出格式 |
| `scripts/` | 代码层 — 运行或改造 | 执行、测试、必要时阅读源码 | Python/JS 脚本、批量转换器 |

禁止放错：模板不放 references/；SOP 不放 templates/；可执行代码不放 references/templates 根下；不放 README.md。

**文件拆分原则**：references/templates/scripts 越细越好——agent 只在需要时读或执行对应文件，不拆 = 每次全读浪费 token。scripts/ 只有重复性强、容易写错、需要确定性执行的逻辑才放；脚本必须有清晰入口和参数说明，新增或修改后至少跑一个代表性样例。

**拆分决策**：单步过长？→ 精炼压缩进 SKILL.md / 需要读后理解？→ 进 references / 需要复制填充？→ 进 templates / 需要运行代码？→ 进 scripts。

## 三、SKILL.md 结构指引

**内容组织顺序**：`# 标题` → `> 摘要` → `## 这个 Skill 做什么`（职责/边界/产物）→ `## 怎么操作`（SOP全内联）→ `## 红线`（第一条必须是读取协议）→ `## 速查表`（有外部文件才设）→ `## 执行模式` → `## 版本`。放不下时优先压缩红线和速查表，保住 SOP 主干。

**执行要点内联写法**（单文件自包含的核心手法）：每个 SOP 步骤节直接写流程细节/检查条件/输出格式/命令模板；与主干重复的删、冗余解释压成表格、同类红线合并；检查条件/红线/输出格式/业务逻辑/脚本调用方式一条不能丢。合入后体量控制在原 SKILL.md+steps 总量的 50-65%。

**速查表设计**：全文件目录引导——每个外部文件什么时候读/执行；无外部文件则不设速查表节。

## 四、精简原则

- **红线≤7条**：只有违反后**断裂下游流程**的才算红线。是红线 ✅：读取协议（截断丢内容）/双文件结构（缺文件平台无法注册）/版本三处一致（平台注册错乱）。不是红线 ❌：frontmatter≤4行、description 含触发词、红线在第一屏（格式偏好，降级为检查清单）。
- **注意力预算**：识别每份文档"最值钱的部分"，核心段占比 ≥30%；不足则辅助段该删的删、该并的并。禁止均匀分配——那是登记表不是设计文档。
- **信息不重复**：同一信息在 SKILL.md 只出现一次；需要强调时引用而非复制。

## 五、用词与表达（照 Mirror 创作专家系列）

skill 文档的语言会传染给下游——文档怎么写，后续写作就怎么说。写 skill 前对照下面六条，每条都是行为指令，正反例对照。

**1. 规则写成行为指令。** 写"做什么/不做什么"，一条一个动作，不写感受评价。
- 差：`保持段落结构清晰`（是感受，执行者不知道怎么办）
- 好：`叙事段 40-120 字（3-5 行手机屏）`（可执行，可检查）

**2. 新概念出现即定义，用"是A，不是B"锁边界。** 第一次出现就说明它是什么、不是什么。
- 差：`AgentSkill 管理创作流程`（没说清和规则、和小说设定有什么区别）
- 好：`AgentSkill 是应用内全局可复用的 AI 工作流程，不是作品规则，也不是故事事实`

**3. 判断给锚点，不给形容词。** 写"以什么判断"，不写"要高质量、要合理"。
- 差：`描述要准确`（怎么算准确？没有判断标准）
- 好：`60% 以上叙事段<40 字 → 段落过碎，触发返工`（有数字，可判定）

**4. 行业词直接用，不自造也不降格。** 已有的词直接叫（agent/skill.json/AskUser），不造黑话（引擎/耦合/闭环），也不改成生活比喻（管饭/撒盘边）。两头都说不清事情：一个装神，一个卖萌。
- 差：`剧情引擎负责推演`（自造词）
- 好：`剧情推演在 plot 环节做`（已有的词直说）

**5. 一段一义，短句为主。** 一段只讲一件事，短句直说，动词开头，能删就删。

**6. 禁 AI 腔。** 不写：值得注意的是/总而言之/首先其次再者/由此可见/综上所述/在当今社会/众所周知。

**判据**：写完拿给没读过本文档的人看，任何一句都能照做、不用追问，才算过关。

**装饰性比喻黑名单**（全仓实测重灾区，直接禁）：
- 禁「XX器/XX引擎」自我定位：`剧情引擎`→剧情推演、`画风测试引擎`→画风测试；技术命名 `-engine` 除外。
- 禁空洞流程名词：闭环→完成/收束/循环，全链路→整条流程；拼图/发生器/孵化器/熔炉/淬炼/乐章/画卷/乐高/车间/摸高→删或换直述。
- 禁装饰性比喻链：不写"构建X生态""打通X链路""结晶沉淀""保驾护航"；改成谁做了什么、产出什么。

## 六、强弱加载保障

skill 文件分两种，读得到的概率不同：

| 保障类型 | 文件 | 机制 | 可靠性 |
|:---------|:-----|:-----|:-------|
| 强保障 | SKILL.md | 平台每次运行强制注入 | 100% |
| 弱保障 | references/templates/scripts | agent 按指引主动读取或执行 | 天然弱 |

**设计原则**：① 设计 SKILL.md 时假设外部资源可能没被读到；② 关键流程（SOP 主干+执行要点）必须在 SKILL.md 自包含；③ 实测 435 runs，3 轮对话后 skill 文件读取率降至 0-3%；④ 断裂后果严重的约束提升到 SKILL.md 红线中。

## 七、创建流程

1. 向用户确认 skill 名称和职责
2. 创建目录 `{skill-name}/`
3. 创建 `SKILL.md`（按三、结构指引）：必须含"这个 Skill 做什么"+"怎么操作"两段且执行要点内联；红线第一条是读取协议；有外部文件则速查表为全文件目录引导
4. 创建 `skill.json`（按一、格式规范）
5. 创建 `CHANGELOG.md`（初始 v1.0.0）
6. 如有 references/templates/scripts 需求，创建对应一级目录
7. 对照九、检查清单逐项验证
8. 输出创建完成报告（文件路径列表）

## 八、改造流程

1. **先读全文** — 用 `Get-Content -Encoding UTF8 -Raw` 读取目标 skill 的 SKILL.md + skill.json + CHANGELOG
2. **输出扫描报告** — 对照九、检查清单标记违规项 + 证据行号，交用户确认
3. **只改结构/格式/红线位置/用词/资源归位** — 不动核心方法论和业务逻辑；发现代码散落时归入一级 `scripts/`；发现 steps 目录时把内容精炼合入 SKILL.md、删目录清引用
4. **版本 +1** — SKILL.md + skill.json + CHANGELOG 三处同步
5. **输出 BEFORE/AFTER 对比报告** — 用户需要知道改了什么

## 九、检查清单

**格式**：frontmatter ≤4 行只留 name+description｜description 含触发条件｜skill.json 七字段完整｜版本三处一致。

**结构**：SKILL.md 含完整 SOP 主干且执行要点已内联，不只是路由表｜"这个 Skill 做什么"说明职责边界产物｜"怎么操作"覆盖全流程动作要点产出｜红线在第一屏、第一条是读取协议、≤7条｜无 steps 目录、无 step 文件引用残留｜知识层归 references/、模板归 templates/、代码归 scripts/。

**加载检查**：速查表是全文件目录引导（列出所有外部文件及读取/执行时机）｜SKILL.md 有强弱加载保障声明｜scripts/ 新增或修改的代表性脚本已实际运行验证。

**文档质量**：识别核心价值段且占比 ≥30%｜同一信息不重复出现｜摘要不堆版本历史（只当前版本一句+CHANGELOG指针）｜无深层嵌套（拍平为 3-6 步扁平流程）｜无第二人称（"You should"改为祈使句）｜**五、用词与表达六条已对照过（行为指令/是A不是B/锚点判断/行业词直用/一段一义/禁AI腔）**。

## 异常与边界条件

| 场景 | 触发条件 | 处理动作 |
|:-----|:---------|:---------|
| 文件/依赖缺失 | 路径无效 | 告知用户，**不准编造数据** |
| 外部工具不可用 | 工具未安装 | 降级方案 |
| 用户中途改变需求 | 用户改变指令 | 暂停当前流程，确认后继续 |
| skill.json 缺失 | 新建时未创建 | 必须补建，不能只有 SKILL.md |
