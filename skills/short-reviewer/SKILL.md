# short-reviewer
> 短篇评审器。读草稿→对照骨架→逐维诊断→输出报告。v2.0.0：steps 三件全合入单文件；9维诊断可派子agent（审查官），主agent校验归位。
## 做什么
输入：正文草稿+骨架卡片+全部前置卡片的流转上下文（自 body-generator）
输出：诊断报告（X.X/10评分+总览+亮点/不足+分维诊断+AI味儿参考+修改建议+总结+是否推荐提交）

## 子agent文件协作协议（方案B）
当本 Skill 由子 agent 运行时（受限环境）：
1. 将诊断报告全文写入临时目录：`{tempDir}/review-{runId}.md`（tempDir 由主agent在调用时传入）
2. 不返回报告全文，只返回结构化元数据：
   ```
   { "file": "{tempDir}/review-{runId}.md", "lines": N, "bytes": N, "head": "前16字符", "tail": "后16字符" }
   ```
3. 主agent校验：文件存在 + 字节数/行数匹配 + head/tail 匹配 → Move-Item 归位到项目目录
4. 校验失败：主agent重新调用子agent重试
## 执行模式
正文通读+9维诊断是典型只读审查工作，天然适配子agent派发（审查官）：子agent按方案B临时落盘报告回元数据，主agent校验归位；Step 1 范围确认与 Step 3 流转确认需用户交互，主agent直执。
## 核心原则
只诊断不修改。评审是对照蓝图执行情况的结构化诊断，不是主观评价。
## 怎么操作（SOP全内联）
> execution.mode: 串行

### Step 1 加载草稿+确认评审范围
1. **提取前置输入**（自 body-generator 流转上下文）：正文草稿全文、选定平台、文章性质、核心约束、脑洞一句话、导语、黄金三句、付费钩子策略、剧情弧线（完整表格）、主角五维、角色清单。
2. **按需加载 references**（见速查表）。
3. **确认评审范围**：默认全篇9维诊断；用户可限定只评某几维（如"只看钩子和节奏"）、只看某一段（如"只看付费钩子断点那段"）、只看AI味儿。话术："默认全篇9维诊断。要限制范围吗？还是直接开始？"
### Step 2 逐维诊断
**诊断流程**（每维执行）：读取对标数据（弧线表对应字段/角色清单/平台规则等）→通读正文相关段→判断执行度（X.X/10）→通过（7.0+）一行确认；不通过（<7.0）标注具体问题+建议方向。

**对标模式**（仅仿写场景——流转上下文带 short-text-deconstructor 拆文报告时启用）：每维评分追加"对标差距"列（当前作品vs例文分差），分差≥2.0标🔴优先修复；对标仅展示差距，不替代独立评分。诊断完输出对标差距汇总表（维度/当前作品/例文/差距/建议）。

**9维诊断检查点**：
| 维度 | 对标 | 诊断检查点 |
|:---|:---|:---|
| 钩子密度 | 弧线表密度标注 | 每段开篇有"必须读下去"元素；段尾留悬念/问题/情绪未闭合；密度与弧线标注一致 |
| 节奏控制 | 弧线表"读者知道/不知道"列 | 信息释放顺序制造悬念；该藏的未提前暴露、该放的未一直藏着；相邻段核心事件不同类重复（重复=节奏循环需打破） |
| 付费钩子 | 付费钩子策略 | 断点位置与策略一致；类型正确（信息缺口/情绪最高点/决策时刻/反转预告）；驱动力强度（强/中/弱）；断点处读者"必须知道后续" |
| 角色塑造 | 主角五维+角色清单 | 主角行为符合底线设定、无违反内在逻辑行为；配角语言风格与标签一致、完成叙事功能；全员有辨识度；有名有姓+有台词角色数超设计人数→检查可否合并 |
| 结局收束 | 弧线收束段设计 | 伏笔全回收；情感闭合；字数在平台范围内；结尾有力度非草草收场；最后情绪高峰后超全文10%字数仍在叙事=拖沓 |
| 文风适配 | writing-styles.md | 语言风格与平台要求一致；句长符合该文风；无其他文风特征"乱入" |
| 情绪张力 | 弧线情绪走向 | 情绪密度达弧线标注；转折有铺垫非突兀；高潮段落张力足够；同类情绪事件（同类反转/打脸）连续使用→标冲击力递减点 |
| 商业驱动 | 综合 | 能否吸引付费；有无明显商业短板；与目标平台付费模式是否适配 |
| AI味儿 | writing-styles.md 去味儿清单 | 总结感句式（含全文扫描密度）/模板句式/过度过渡/抽象描写/AI式对话/百科口吻/段落对称性；标注位置（段号+句子）+类型+修改方向。仅参考不纳入评分 |

### Step 3 输出评审报告
按 `templates/review-report.tpl.md` 结构填充：
1. **总览卡片**：X.X/10评分（8个非AI味儿维度的加权综合）+等级（见等级表）+一句话总评
2. **亮点** 2-3条、**不足** 1-3条：每条一句话+简短展开
3. **分维诊断摘要**：每维一行"维度名称｜X.X/10｜✅通过 / 🔶问题数"
4. **AI味儿参考**：位置+类型+建议方向
5. **总结**：综合评分/等级/结论（推荐提交 / 修完可提交 / 需要大修）/最强武器/最弱一环
6. **流转确认**："以上是我完整的诊断。你想改哪些？确认后进入润色。"

## 等级
| 分数 | 等级 | 含义 |
|:---|:---|:---|
| 9.0-10 | 现象级 | 编辑抢着签 |
| 8.0-8.9 | 爆款区 | 微调一两处就能投 |
| 7.0-7.9 | 潜力带 | 底子对，修完能上8 |
| 6.0-6.9 | 过关线 | 能投但竞争激烈 |
| 5.0-5.9 | 危险区 | 脑洞或执行有问题 |
| 5.0以下 | 别急着投 | 建议从脑洞或平台重新考虑 |

## 红线
| # | 红线 | 违反后果 |
|:-:|:-----|:---------|
| 1 | 只诊断不修改——不替用户直接改正文 | 用户失去对作品的控制 |
| 2 | 每条诊断必须配建议方向，不能只说"XX不行" | 诊断无用，用户不知道怎么办 |
| 3 | AI味儿不纳入评分，仅作参考标注 | 干扰真实质量判断 |
| 4 | 分维诊断必须对标具体的前置卡片数据 | 评审变成主观评价 |
