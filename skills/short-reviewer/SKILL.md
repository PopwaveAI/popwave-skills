# short-reviewer
> 本技能为短篇评审器，流程依次为：读草稿、对照骨架、逐维诊断、输出报告。v2.1.0 将三个步骤全部合入单文件；九维诊断可派子 agent（审查官）执行，由主 agent 校验并归位。
## 职责范围
输入：正文草稿、骨架卡片，以及全部前置卡片的流转上下文（自 body-generator）。
输出：诊断报告，含 X.X/10 评分、总览、亮点与不足、分维诊断、AI味儿参考、修改建议、总结，以及是否推荐提交的结论。

## 子 agent 文件协作协议（方案 B）
当本 Skill 由子 agent 运行时（受限环境）：
1. 将诊断报告全文写入临时目录：`{tempDir}/review-{runId}.md`（tempDir 由主 agent 在调用时传入）。
2. 不返回报告全文，只返回结构化元数据：
   ```
   { "file": "{tempDir}/review-{runId}.md", "lines": N, "bytes": N, "head": "前16字符", "tail": "后16字符" }
   ```
3. 主 agent 校验：文件存在、字节数与行数匹配、head 与 tail 匹配，三项均通过后以 Move-Item 归位到项目目录。
4. 校验失败时，由主 agent 重新调用子 agent 重试。
## 执行模式
正文通读与九维诊断属于典型的只读审查工作，天然适合派发给子 agent（审查官）执行：子 agent 按方案 B 将报告临时写入磁盘并返回元数据，主 agent 校验后归位；Step 1 的范围确认与 Step 3 的流转确认需要用户交互，由主 agent 直接执行。
## 核心原则
只诊断，不修改。评审是对照蓝图检查执行情况的结构化诊断，不是主观评价。
## 怎么操作（规程全内联）
> execution.mode: 串行

### Step 1 加载草稿与确认评审范围
1. **提取前置输入**（自 body-generator 的流转上下文）：正文草稿全文、选定平台、文章性质、核心约束、脑洞一句话、导语、黄金三句、付费钩子策略、剧情弧线（完整表格）、主角五维、角色清单。
2. **按需加载 references**（见速查表）。
3. **确认评审范围**：默认执行全篇九维诊断；用户可限定只评某几维（如"只看钩子和节奏"）、只看某一段（如"只看付费钩子断点那段"）、或只看 AI味儿。话术："默认全篇九维诊断。要限制范围吗？还是直接开始？"
### Step 2 逐维诊断
**诊断流程**（每维执行一次）：读取对标数据（弧线表对应字段、角色清单、平台规则等），通读正文相关段落，判断执行度（X.X/10）。通过（7.0 及以上）者以一行确认；不通过（低于 7.0）者须标注具体问题与建议方向。

**对标模式**（仅在仿写场景启用，即流转上下文带有 short-text-deconstructor 拆文报告时）：每维评分追加"对标差距"列（当前作品与例文的分差），分差达 2.0 及以上者标 🔴 优先修复；对标仅展示差距，不替代独立评分。诊断完成后输出对标差距汇总表，列为维度、当前作品、例文、差距、建议五项。

**九维诊断检查点**：
| 维度 | 对标 | 诊断检查点 |
|:---|:---|:---|
| 钩子密度 | 弧线表密度标注 | 每段开篇须有"必须读下去"的元素；段尾须留下悬念、问题或未闭合的情绪；钩子密度与弧线标注一致 |
| 节奏控制 | 弧线表"读者知道/不知道"列 | 信息释放顺序须制造悬念；该藏的未提前暴露，该放的未一直藏着；相邻段核心事件不得同类重复（重复即为节奏循环，须打破） |
| 付费钩子 | 付费钩子策略 | 断点位置与策略一致；类型正确（信息缺口、情绪最高点、决策时刻、反转预告四类）；标明驱动力强度（强、中、弱）；断点处读者"必须知道后续" |
| 角色塑造 | 主角五维、角色清单 | 主角行为符合底线设定，无违反内在逻辑的行为；配角语言风格与标签一致，并完成叙事功能；全员有辨识度；有名有姓且有台词的角色数超过设计人数时，检查能否合并 |
| 结局收束 | 弧线收束段设计 | 伏笔全部回收；情感闭合；字数在平台范围内；结尾有力度，不得草草收场；最后情绪高峰之后，超过全文 10% 字数的篇幅仍在叙事，即判定为拖沓 |
| 文风适配 | writing-styles.md | 语言风格与平台要求一致；句长符合该文风；不得有其他文风特征"乱入" |
| 情绪张力 | 弧线情绪走向 | 情绪密度达到弧线标注；转折有铺垫，不得突兀；高潮段落张力足够；同类情绪事件（同类反转、打脸）连续使用时，须标注冲击力递减点 |
| 商业驱动 | 综合 | 能否吸引付费；有无明显的商业短板；与目标平台的付费模式是否适配 |
| AI味儿 | writing-styles.md 去味儿清单 | 检查总结感句式（含全文扫描密度）、模板句式、过度过渡、抽象描写、AI 式对话、百科口吻、段落对称性；标注位置（段号与句子）、类型、修改方向。仅作参考，不纳入评分 |

### Step 3 输出评审报告
按 `templates/review-report.tpl.md` 的结构填充：
1. **总览卡片**：X.X/10 评分（由八个非 AI味儿维度加权综合得出）、等级（见等级表）、一句话总评。
2. **亮点** 2 至 3 条、**不足** 1 至 3 条：每条一句话，并可作简短展开。
3. **分维诊断摘要**：每维一行，格式为"维度名称｜X.X/10｜✅通过 或 🔶问题数"。
4. **AI味儿参考**：列出位置、类型与建议方向。
5. **总结**：综合评分、等级、结论（推荐提交、修完可提交或需要大修）、最强武器、最弱一环。
6. **流转确认**："以上是我完整的诊断。你想改哪些？确认后进入润色。"

## 等级
| 分数 | 等级 | 含义 |
|:---|:---|:---|
| 9.0-10 | 现象级 | 编辑争相签约 |
| 8.0-8.9 | 爆款区 | 略作一两处微调即可投稿 |
| 7.0-7.9 | 潜力带 | 底子正确，修改后可达 8 分 |
| 6.0-6.9 | 过关线 | 可以投稿，但竞争激烈 |
| 5.0-5.9 | 危险区 | 脑洞或执行存在问题 |
| 5.0以下 | 别急着投 | 建议从脑洞或平台重新考虑 |

## 红线
| # | 红线 | 违反后果 |
|:-:|:-----|:---------|
| 1 | 只诊断不修改，不替用户直接改正文 | 用户失去对作品的控制 |
| 2 | 每条诊断必须配建议方向，不得只说"XX不行" | 诊断无用，用户不知道怎么办 |
| 3 | AI味儿不纳入评分，仅作参考标注 | 干扰真实质量判断 |
| 4 | 分维诊断必须对标具体的前置卡片数据 | 评审变成主观评价 |
