# PRD · tool-split-chapters

## 解决什么问题（带凭据）

拆书管线在「分章」这一环断链：`pop-decon-dimension` 的 L1 分批精读要求读 `_temp/chapters/chXXX.txt`（`references/delegation-orchestration.md` 第 32 行），但全仓 `.py/.mjs/.js/.ps1` 搜索零命中，没有任何代码生成这个目录。`.gitignore` 残留 `library/知名小说wiki/诡秘之主/_temp/chapters/` 说明历史上是手工生成的，没沉淀成代码。

断链的后果不是少一步，而是 L1 门禁第 2 项（锚点池覆盖、命中章不少于 20 章）直接失效——章号错位或缺失时，锚点池整体不可信，下游六模块全废。

## 解决思路（每步为什么必须这样）

1. **分章做成确定性脚本，不做 AI 判断**。分章是重复性强、容易写错、需要确定性执行的逻辑，符合 `pop-shared-skill-create` 对 `scripts/` 的定位。同一输入必须逐字节一致，AI 介入会破坏可复现性。
2. **章号以分章序号为准**。站点普遍缺号重号，标题内嵌数字不可作定位。用 `globalNo` 连续编号，卷内序号 `volumeLocalNo` 单独编号，缺号重号进 `quality` 字段告警而非硬报错。
3. **产出合并章节索引作为唯一接口**。UI 只读它渲染卷章选择器，拆解层只读它拿章清单，两边不碰正文，保证「UI 看到的章」与「拆解读到的章」天然一致。
4. **切批、范围校验、token 估算同脚本**。它们都只依赖章节索引，放一起避免拆成多个入口；token 估算让「启动前展示预估」不依赖另一次计算。

## 关键取舍

| 选了什么 | 放弃了什么 | 为什么 |
|:--|:--|:--|
| 行首正则识别标题 | 不解析爬取目录、不做语义判断 | 爬取目录在 `tool-download-webnovel` 侧，本脚本只消费 TXT；语义判断引入不确定性 |
| 无标题文本直接报错 | 不用 AI 猜切点 | 猜测切点会导致锚点错位，且必须用户确认，违背确定性原则 |
| 缺号重号进 `quality` 告警 | 不自动补号或删章 | 自动修补会掩盖源数据问题，告警让用户在 UI 里修正边界 |
| 系数 [0.6, 1.0] 估算 token | 不逐字精确计数 | 精确计数依赖特定 tokenizer，与运行环境解耦；区间估算够预估用 |

## 不做什么

- 不下载 TXT（`tool-download-webnovel` 的活）。
- 不拆解、不提取八维（`pop-decon-dimension` 的活）。
- 不做范围征询、不做沉淀（`pop-decon` 的活）。
- 不产出批次完成标志（`pop-decon-dimension` 的活）。
