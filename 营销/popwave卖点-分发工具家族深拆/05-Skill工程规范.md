## 0. 一句话卖点

**popwave 把"建一个 AI Skill"做成有工程规范的活：五类资源分层（SKILL.md/steps/references/templates/scripts）各归其位、SKILL.md 自包含不依赖弱保障文件也能跑、红线只留≤7条断裂级、强弱加载保障关键规则永不失效、六步创建+五步改造+BEFORE/AFTER可审计、版本三处一致——不是"写个 prompt"，是"造一个能注册、能触发、能稳定交付的引擎"。**

## 1. 用户痛点：Skill 越写越乱、改了失效、交付后才漏字段

| 痛点 | 表现 | 后果 |
|---|---|---|
| **文件混乱** | 标准和代码混一起、README 乱飞 | 下游难解析 |
| **改了失效** | 核心规则藏在次要文件，没被读到 | 运行崩 |
| **规则稀释** | 红线一大堆，重点被稀释 | 等于没红线 |
| **交付漏字段** | 版本不一致、description 无触发词 | 注册/触发错乱 |
| **改造失控** | 重构时误改业务方法论 | 核心逻辑被毁 |

> 核心焦虑：SKILL 是 popwave 的引擎单元——工程规范决定"引擎能不能造好、造完能不能跑、改造时会不会被毁"。

## 2. 关键认知：Skill 规范的本质是"让引擎可注册、可触发、可稳定交付"

高质量 Skill = 五类资源分层责任清晰 + SKILL.md 自包含（骨架/红线/速查表都在第一屏）+ 红线≤7 只留断裂级 + 强弱加载保障 + 六步创建/五步改造双流程 + 版本三处一致——**不是内容多好，是结构永远不坏、改动能审计**。

## 3. 反面教材：大而全、弱保障、乱改方法论

- **规则堆成山**：红线 20 条，等于没红线。
- **关键约束放次要文件**：agent 没读到，执行断裂。
- **重构顺手改业务**：只该动结构却把核心方法论改了。
- **版本各处飘**：SKILL.md/skill.json/CHANGELOG 版本不一致，无法判断最新。
> 正确做法：见第 4 节——五层分层 + 自包含 + 红线≤7 + 强弱保障 + 双流程可审计。

## 4. 机制：五层分层 + 自包含 + 红线≤7 + 强弱保障 + 拆分决策树 + 双流程 + 版本一致 + 检查清单

### 4.1 五类资源分层（核心）
SKILL.md 骨架层（≤100行，SOP骨架/红线/速查表/版本）；steps/ 展开层（50-150行/文件）；references/ 知识层（读后理解的方法论）；templates/ 模板层（复制填充）；scripts/ 代码层（可执行脚本）——**每种资源各归其位**。

### 4.2 SKILL.md 自包含（核心，小巧思）
设计时假设 steps/references/templates 可能没被读到，核心 SOP 骨架 + 断裂级红线必须在 SKILL.md 自包含；「怎么运作」写 step1~n 简述——**不是纯路由表，agent 不读外部文件也知道完整流程**。

### 4.3 红线≤7，只留断裂级（小巧思）
只有违反后断裂下游的才叫红线；格式/风格/细节降级为检查清单（frontmatter≤4行、description 含触发词、红线位置等不算红线）——**少而难，重点不被稀释**。

### 4.4 强弱加载保障（小巧思）
SKILL.md 由 host 每次 run 强制注入（可靠性100%，强保障）；steps/references/templates/scripts 靠 agent 主动读（天然弱保障）。**约束断裂后果严重的，必须提升到 SKILL.md 红线，不留弱保障文件里**。

### 4.5 拆分决策树 + 目录禁用
骨架不足?进 SKILL.md；单步过长→steps/；读后理解→references/；复制填充→templates/；可执行→scripts/。**templates 不放 references、SOP 不放 templates、可执行代码不进 references/templates 根**；禁用 README.md。

### 4.6 六步创建流程（核心）
确认名称/触发场景/核心产物/下游消费者→确认职责与触发条件→抽象骨架（换皮测试）→规划结构→落盘 SKILL.md+skill.json+CHANGELOG.md→一致性校验（description触发/版本三处/速查表覆盖/弱保障读取时机）。

### 4.7 五步改造流程（小巧思）
读全文（UTF8 -Raw）→输出扫描报告（对照清单标违规+证据行号）→**只改结构/格式/红线位置/资源归位，不擅自改业务方法论**→版本+1三处同步→输出 BEFORE/AFTER 对比报告可审计。

### 4.8 检查清单四维 + 版本三处一致
格式（frontmatter≤4/触发词/字段/版本一致）+ 结构（≤100行/完整SOP/红线第一屏/≤7条/细节下沉/代码进scripts）+ 加载门禁（速查表全目录引导/step末尾加载门禁）+ 文档质量（核心段≥30%/信息不重复/无深层嵌套/无第二人称）——版本 SKILL.md+skill.json+CHANGELOG 三处一致。

### 4.9 description 必含触发条件
「当用户说…时启用」+ 做什么/何时触发/产出给谁——**触发条件本身具备检索价值**，不是任意描述。

## 5. 可测量 / 门禁

| 门禁 | 口径 |
|---|---|
| **五层归位** | 每类文件只进应进目录 |
| **SKILL.md** | ≤100行、自包含完整性可独立执行 |
| **红线** | ≤7 条，仅断裂级 |
| **版本** | SKILL.md/skill.json/CHANGELOG 三处一致 |
| **改造审计** | 只动结构 + BEFORE/AFTER 对比报告 |
| **检查清单** | 格式/结构/加载门禁/文档质量四维 |

## 6. 深度：Skill 工程规范是"popwave 引擎"的制造标准
popwave 全家 50+ skill 都由本规范约束。**营销价值**：它把"造 AI 能力"标准化——每个新 skill 都能注册、触发、稳定交付，改造可审计、版本可溯，是整套产线可复制扩张的地基。

---

## 7. 操作顺序（创建：先定义再落盘；改造：先审计再动手）
创建：确认名称/场景/产物/下游→职责触发→抽象骨架→规划结构→落盘三文件→一致性校验。
改造：读全文→扫描报告(带行号)→只动结构不碰业务→版本+1三处同步→BEFORE/AFTER 报告。
