## 0. 一句话卖点

**popwave 的拆书产出走"双轴可选"：输出格式（precision 精品设计包 / fast 瘦身白描卡）× 处理方式（quality 每章子agent / performance 每30章子agent）。模式开启前强制向用户说明得失，187 章 fast 模式实测约 3-4 分钟、压缩比约 11%、678 章全书约 12 分钟。要精品要快，一次问清。**

## 1. 用户痛点：拆书产出"一刀切，要么太慢要么太浅"

| 痛点 | 表现 | 后果 |
|---|---|---|
| **深度不可选** | 要精拆全书，慢到不可接受 | 用户放弃 |
| **成本不透明** | 不知道要跑多久、几个子agent | 预算失控 |
| **输出漂移** | 子agent各出一套格式 | 批量不可用 |
| **锚点补全乱** | 下游看到"升级"自行脑补数值 | 产出偏差 |

> 核心焦虑：拆书引擎要被规模化使用，必须让用户在"深度×速度"之间**自己权衡**，且产出格式稳定可控、锚点精度不丢。

## 2. 关键认知：拆书产出要"双轴权衡 + 强制确认 + 稳定可批"

高质量拆书交付 = 输出格式（precision/fast）与处理方式（quality/performance）可自由组合、**开启前强制确认并说明得失**、格式规范化（防子agent漂移）、精度锚点下钻防下游脑补。用户选择即成本可控。

## 3. 反面教材：把拆书产出做成"不可选的黑盒"

- **默认全质量**：直接跑 187 字 agent 精拆，45 分钟等不起。
- **不问用户**：不说明精品/快速、质量/性能的得失就开跑。
- **格式漂移**：第一批嵌了格式规范，后续批次"参见之前"，最后 5 套格式。
- **锚点靠脑补**：白描卡写"升级"，下游 render 自己换成"获得属性增益"。
> 正确做法：见第 4 节——双轴可组 + 强制确认 + 格式物理嵌入 + 精度锚点。

## 4. 机制：双轴组合 + 强制确认 + precision/fast + 子agent派发 + 格式归一 + token预算

### 4.1 双轴架构（小巧思）
- **输出格式**：precision = v4 设计包（3层+1区），单章 1-2K、压缩比 80-100%；fast = 瘦身白描卡（4段式），单章 150-400、压缩比约 11%。
- **处理方式**：quality = 每章 1 子 agent；performance = 每 30 章 1 子 agent 合并。

### 4.2 任务开启前强制模式确认
每次开启前确认 strategy + mode，**说明质量模式与性能模式、precision 与 fast 的得失**，取得明确选择才继续——避免默认执行导致用户没想到成本或精度损失。

### 4.3 precision 模式——v4 设计包（3 层 +1 区）
每章输出：beat 链 / 爽点设计 / 角色与人设 / 设定物品提取区。beat 表 7 列：`#/beat/类型/scene/POV/参与角色/原文证据`；每 beat 需 scene+POV+原文证据+感官锚点。适合精品拆书、拆书为写、prose-render 直接消费。

### 4.4 fast 模式——瘦身白描卡（4 段式）
每章独立 Markdown：事件白描(3-5句)/ 关键数据(🔒一行摘要+定位指针)/ 爽点·钩子 / 人物关系变化(可选)。单章目标 150-250 字上限 500。适合大规模拆书、快速验证、全书骨架。

### 4.5 实测性能（给用户算账）
quality 模式 187 章 = 187 子 agent，约 35-45 分钟；performance 模式 187 章 = 7 子 agent，约 3-4 分钟；fast 模式 187 章压缩比约 11%；678 章全书约 12 分钟。

### 4.6 本子 agent 派发，不走 DEEPSEEK API
v6.4.0 起从脚本直连 DS API 改为派发子 agent——主 agent 派发，每个读原文章节产出白描卡/设计包，无 DEEPSEEK_API_KEY 依赖，流程透明、按批次并行。

### 4.7 精度锚点 4 字段
每 beat 加 scene / POV / 关键对白数据 / 感官锚点。scene 定位 DNA 场景卡；POV 锁定感知锚点；关键对白用不可替代原文；**感官锚点写具体物理感觉，不写抽象**——避免 render 对"升级"自行脑补。

### 4.8 格式注入失败复盘 + 格式后处理归一化（小巧思）
- 教训：海贼法典 32 章设计包出现 5 种格式，根因是格式规范只在第一批物理嵌入、后续"参见之前"——**格式规范必须物理嵌入每个子agent context，禁止引用**。
- 后处理：并行提取后对设计包归一化（首行 `# 设计包 — chXXX「标题」`、小节命名映射，从源章节文件提取标题）——子agent 输出漂移由系统自动修复。

### 4.9 子agent 上下文预算三层防护
预拆分（避免子agent 浪费约 20K tokens 定位章节）→ 批次≤3章 → 预算优先级（L1 beat 链层不被裁剪）——防长章拆解后段退化。

## 5. 可测量 / 门禁

| 门禁 | 口径 |
|---|---|
| **双轴可组** | precision/fast × quality/performance |
| **强制确认** | 开启前说清得失，取得选择 |
| **格式物理嵌入** | 规范嵌每子agent context，禁"参见之前" |
| **精度锚点** | scene/POV/关键数据/感官锚点4字段 |
| **实测可报** | quality 45分 / performance 3-4分(fast 187章) |

## 6. 深度：双轴引擎让拆书"按需规模化"
喂给 plot/world/write/seed（prose-render 直接消费 precision；快速验证走 fast）。**营销价值**：它给了"精品与快速、深度与成本"的显式开关，用户敢拆 678 章全书——规模化拆书不再被性价比劝退。

---

## 7. 操作顺序（先确认，再组合，再派发，再归一）
征询输出格式(quality/fast)+处理方式(quality/performance)并说明得失 → 确认 → 派发子agent（每子agent物理嵌入格式+规格）→ 精度锚点4字段 → 并行/批处理 → 格式后处理归一化 → token预算兜底。

## 9. 竞品差异锚（一句话）
市面拆书产出 = 深/浅一刀切/不问成本/格式漂移/锚点脑补；popwave 设计包 = **precision/fast×quality/performance 双轴 + 强制确认 + 格式物理嵌入+归一化 + 精度锚点4字段 + 实测速度可报**。
